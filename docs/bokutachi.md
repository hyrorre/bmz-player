# Bokutachiへの単曲スコア送信

BokutachiのDirect Manual APIへ、BMZ Playerで新しくプレイした単曲の成績を送信します。
BMZ Playerは独立したクライアントとして送信し、LR2やbeatorajaを名乗りません。

## 接続する

1. Bokutachiで、`submit_score`権限を持つAPIキーを発行します。
2. 「BMZ メニュー → IR → Bokutachi」の「APIキー」へ入力し、「キーを検証して保存」を押します。
3. アカウントが表示されたら送信方針を選びます。既定は無効で、接続後も送信専用です。

「接続を再確認」でキーの有効性と権限を確認できます。「APIキーを削除」でローカルのキーを削除します。
キーの更新は、削除後に新しいキーを検証して保存してください。同じアカウントなら待機中の送信を再開できます。
別アカウントへ変更しても、以前のアカウントのジョブを新しいアカウントへ送信しません。
受付済みのインポートは、元のアカウントへの登録結果を確認します。

APIキーは既存の秘密情報保存先（ファイルまたはOSの資格情報ストア）を使います。
プロファイル設定・送信本文・ログには保存しません。キーにrefresh token処理は行いません。
接続確認ではHTTP成功だけでなく、APIの成功、ユーザーID、`submit_score`権限を確認します。

CLIでは次を実行し、非表示の入力欄へAPIキーを入力します。キーをコマンド引数に書かないでください。

```sh
bmz ir login --provider bokutachi
bmz ir status
bmz ir logout --provider bokutachi
```

## 送信できるプレイ

| 元譜面と本人の採点モード | RULE MODE | 送信先 |
| --- | --- | --- |
| 7K | LR2oraja | BMS 7K |
| 14K | LR2oraja | BMS 14K |
| 9K | beatoraja | PMS ControllerまたはKeyboard |

すべてのモードで、保存されたLN区分が`ForceLn`となるプレイが対象です。
AUTO(LN)でも、未定義LNと明示LNが混在する譜面などで正規化結果が`ForceLn`なら送信できます。
設定画面のAUTO／FORCEという名前や元譜面のCN／HCNの有無だけでは判断しません。
最終的には、Bokutachiに登録された譜面と本人の全曲分の採点ノーツ数が一致する必要があります。

[通常スコアの保存・実効アシスト条件](score-persistence.md)を満たす必要があります。
全体AUTOPLAY、本人のリプレイ再生、Practice、キー変換（7→9など）、BATTLE／BATTLE ASは送信しません。
DP FLIPは対象です。ADD LNは設定名だけで除外せず、採点ノーツ数の照合で判断します。
ASSIST EASYゲージのランプと、実際に適用されたアシストは別に扱います。
FAILEDも送信方針の条件を満たせば対象です。

原譜面に`#RANDOM`／`#SETRANDOM`／`#SWITCH`／`#SETSWITCH`がある譜面は対象外です。
これはプレイ時の配置RANDOMとは別です。配置はNORMAL、MIRROR、RANDOM、R-RANDOM、S-RANDOMに対応し、
F-RANDOM／MF-RANDOMは送信時のメタデータだけRANDOMにまとめます。ローカル・他IRの値は変えません。
正確に表せない既知の配置は配置メタデータを省略します。DPは左右をセットで扱います。
seed、FLIPの独自フィールド、配置を再現できるという保証は送りません。

表示だけのG-BATTLEは、元譜面と本人の採点範囲が7Kで、2P表示専用レーンを除外した
採点ノーツ数が保存結果と一致すると確認できる場合に送信します。送信先はBMS 7Kです。
相手のノーツ数・配置・判定を混ぜず、相手リプレイの存在を本人のリプレイ再生と混同しません。

## PMSの入力機器とUPDATE SCORE

PMSは結果保存時にBMZが確定した入力機器区分を使います。
Controllerは`pms-controller`、Keyboardは`pms-keyboard`へ送信します。
物理寸法の自動判定、機種の許可リスト、専用の申告設定は追加していません。
**TachiのController部門はACサイズのコントローラーを前提としています。**
BMZの入力分類により送信先が決まる点を確認して利用してください。

UPDATE SCOREは、同じ譜面・LN区分・DOUBLE区分・ルール・入力機器の過去ローカル成績と比較します。
EX・ランプ・最大コンボは最大、BP・CBは最小を独立に集計し、いずれかの改善で送信します。
同じ入力機器の履歴がなければ初プレイとして送信します。KeyboardのBESTでControllerの初投稿を抑制しません。
比較に今回の履歴は含めません。ローカル全体のBESTや他IRの区分は変わりません。

新しいBokutachiアカウントに未投稿でも、同じ入力機器の過去ローカル成績を更新しなければ
UPDATE SCOREでは送信しません。ALWAYSとCOMPLETE SONGの意味は既存IRと同じです。
作成済みジョブの再試行時には、BEST更新判定や入力機器の判定をやり直しません。

## 譜面の照合

7K／14Kは元ファイルのSHA256でBokutachiの譜面を解決します。
PMSは公開ハッシュ検索から、入力機器区分・SHA256・CHART・primaryが一致する候補を選び、
候補のsong IDで再解決します。chart ID・game・SHA256・採点ノーツ数を再確認し、
送信本文でも同じ`tachiSongID`と`difficulty: "CHART"`を使用します。

未登録、候補の曖昧さ、ハッシュや採点ノーツ数の不一致は理由を表示して停止します。
「採点ノーツ数不一致」は、本人の全曲分の採点対象数がBokutachiの登録数と異なるという意味です。
判定数の合計（空POORを含む）、途中まで通過した数、G-BATTLEの相手を含む表示用ノーツ数とは比較しません。
比率補正・ノーツ数の書き換え・別ハッシュへの置換・譜面の自動登録はしません。
後日登録・修正された場合は送信キューから手動で再送信すると再照会します。
送信キューのprovider選択でBokutachiを選びます。ランキング用primaryの指定は不要です。
「完了（登録成功・新規追加なし）」で終端結果や警告を確認できます。

## 受付と登録完了

1リクエストで1スコアを送ります。「受付」は登録完了ではありません。
受付後はimport IDを保存し、短いGET確認を繰り返します。再起動や通信失敗後も、そのIDの確認から再開します。
既知のimport IDがあるジョブは、手動再試行でもスコアのPOSTを繰り返しません。

- スコアIDが1件確認できた場合：登録成功。警告があれば保持して表示します。
- スコアIDがなくエラーがある場合：登録失敗。理由を保持します。
- スコアIDもエラーもない場合：「新規追加なし（重複等）」。新規追加を確認できなかった終端結果です。
  重複と断定するものではなく、新規成功にも数えません。自動再送しません。
- 応答の欠落・型不正・アカウント不一致：確認異常として停止します。成功扱いにはしません。

401／403はキーと権限の修正が必要です。429は待機時間を尊重し、同じoriginへのPOSTを待機させます。
通信失敗・408・5xxは既存の上限付きバックオフで再試行します。受付直後のpoll 404は120秒の猶予内で
GETを再試行し、継続する場合はimport IDを保持したまま自動確認を止めます。
POSTの応答を受信できずimport IDが不明な場合は、保存した内容・時刻のまま再送します。
Tachiにないidempotencyヘッダーは使わず、必ず一度だけ登録されるとは保証しません。

## 対象外の機能

過去ローカルスコアの一括送信、コース全体・各ステージ、ランキング・ライバル・リプレイ・
G-BATTLE対戦データの取得、リプレイアップロード、attestationは未対応です。
「新規プレイのみ」は過去履歴から送信ジョブを新しく作らないという意味です。
新規プレイから作成済みのジョブは、日をまたいだ再試行でも処理します。

Bokutachiはランキング用primaryへ自動選択しません。設定ファイルでprimaryに指定しても
ランキング取得は行いません。「IRページを開く」は確実なBokutachiのトップページへ案内します。

## 保存データと実装

組み込み4枠目へBokutachiを追加し、既存カスタム設定は後続へ移します。既存provider key、認証情報、primaryは保持します。
新しいBokutachiジョブの専用contextに、元モード・本人の採点モード・キー変換・採点範囲・送信先game・originを固定します。
旧payloadの欠けた情報は推測しません。他IRのpayloadや既存リプレイは変更しません。

network DB v7は、固定した送信本文・解決済み外部ID・import ID・段階を既存ジョブとは別のテーブルへ保存します。
次回時刻・診断は既存outboxへ保存します。APIキーを含まない受付receiptもローカルへ保存し、受付後のDB書込み失敗からの復旧に使います。
score DB v35は通常BEST更新対象の履歴識別と入力機器別集計の索引を追加します。
LNの旧Auto／Force互換検索、過去スコアの再正規化・統合、外部DB再インポートの重複修復は行いません。

実装は`ir/bokutachi/`、結果確定は`screens/play_finish.rs`、機器別比較は`storage/score_db/device_best.rs`です。
検証とAPI契約の根拠は[作業記録](../notes/2026/2026-11-09-bokutachi-submission.md)を参照してください。
