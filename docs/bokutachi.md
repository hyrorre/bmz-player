# Bokutachiのスコア送信・ランキング・段位更新

BokutachiのDirect Manual APIへ、BMZ Playerで新しくプレイした単曲の成績を送信します。
BMZ Playerは独立したクライアントとして送信し、LR2やbeatorajaを名乗りません。
コース各曲の単曲スコア送信と、登録済みBMS段位の更新にも対応します。

## 接続する

1. Bokutachiで、`submit_score`権限を持つAPIキーを発行します。
2. 「BMZ メニュー → IR → Bokutachi」の「APIキー」へ入力し、「キーを検証して保存」を押します。
3. アカウントが表示されたら送信方針を選びます。ゲーム内でBokutachiのランキングを見るには、同じIR設定でPrimaryにBokutachiを選びます。

「接続を再確認」でキーの有効性と権限を確認できます。「APIキーを削除」でローカルのキーを削除します。
キーの更新は、削除後に新しいキーを検証して保存してください。同じアカウントなら待機中の送信を再開できます。
別アカウントへ変更しても、以前のアカウントのジョブを新しいアカウントへ送信しません。
受付済みのインポートは、元のアカウントへの登録結果を確認します。

APIキーは既存の秘密情報保存先（ファイルまたはOSの資格情報ストア）を使います。
プロファイル設定・送信本文・ログには保存しません。キーにrefresh token処理は行いません。
接続確認ではHTTP成功だけでなく、APIの成功、ユーザーID、`submit_score`権限を確認します。

CLIでは次を実行し、非表示の入力欄へAPIキーを入力します。キーをコマンド引数に書かないでください。

```sh
bmz ir login --provider bokutachi
bmz ir status
bmz ir logout --provider bokutachi
```

## 送信できるプレイ

| 元譜面と本人の採点モード | RULE MODE | 送信先 |
| --- | --- | --- |
| 7K | LR2oraja | BMS 7K |
| 14K | LR2oraja | BMS 14K |
| 9K | beatoraja | PMS ControllerまたはKeyboard |

すべてのモードで、保存されたLN区分が`ForceLn`となるプレイが対象です。
AUTO(LN)でも、未定義LNと明示LNが混在する譜面などで正規化結果が`ForceLn`なら送信できます。
設定画面のAUTO／FORCEという名前や元譜面のCN／HCNの有無だけでは判断しません。
最終的には、Bokutachiに登録された譜面と本人の全曲分の採点ノーツ数が一致する必要があります。

[通常スコアの保存・実効アシスト条件](score-persistence.md)を満たす必要があります。
全体AUTOPLAY、本人のリプレイ再生、Practice、キー変換（7→9など）、BATTLE／BATTLE ASは送信しません。
DP FLIPは対象です。ADD LNは設定名だけで除外せず、採点ノーツ数の照合で判断します。
ASSIST EASYゲージのランプと、実際に適用されたアシストは別に扱います。
FAILEDも送信方針の条件を満たせば対象です。

原譜面に`#RANDOM`／`#SETRANDOM`／`#SWITCH`／`#SETSWITCH`がある譜面は対象外です。
これはプレイ時の配置RANDOMとは別です。配置はNORMAL、MIRROR、RANDOM、R-RANDOM、S-RANDOMに対応し、
F-RANDOM／MF-RANDOMは送信時のメタデータだけRANDOMにまとめます。ローカル・他IRの値は変えません。
正確に表せない既知の配置は配置メタデータを省略します。DPは左右をセットで扱います。
seed、FLIPの独自フィールド、配置を再現できるという保証は送りません。

表示だけのG-BATTLEは、元譜面と本人の採点範囲が7Kで、2P表示専用レーンを除外した
採点ノーツ数が保存結果と一致すると確認できる場合に送信します。送信先はBMS 7Kです。
相手のノーツ数・配置・判定を混ぜず、相手リプレイの存在を本人のリプレイ再生と混同しません。

## KaleidBeat拡張の送信条件

`.bmc`という拡張子だけでは除外しません。表示・音声・小節線・CNOBJ/HCNOBJの終端音は、
下記の既知の解釈情報と既存のForceLn・ルール・アシスト・登録譜面照合条件を満たせば対象です。

元HLNを**FORCE LNへ変換した結果**も、保存区分がForceLn、実効種別がLN、実効HLNが残っていない場合に対象とします。
原本SHA256/MD5を維持し、本人の全曲分の採点ノーツ数が登録値と一致することを確認します。
元HLNの情報はローカルの送信証拠へ残します。AUTOでHLNが残る結果、FORCE CN/HCNは対象外です。

動的分岐・フリーゾーン・ポーション・ダミーは、元譜面または実効譜面に存在すれば対象外です。
EXTRA NOTE等の変換や、今回はその枝を選ばなかったという理由では許可しません。
宣言のみでオブジェクトがない場合と、静的RANDOMで不採択の枝は元機能に含めませんが、
元譜面に静的RANDOMがある場合の既存除外は別に適用します。
部分対応・不正拡張、解釈情報の欠落・version 0・未知版も送信を保留します。

この条件は新規単曲・コース各曲・段位・永続キュー・CLI／個別再送に適用します。
段位API自体は変換HLNの採点数を検査しないため、該当ステージをSHA256で解決し、
保存した実採点数と登録値を照合してから段位を送ります。段位の既存4曲・配置・ゲージ条件も必要です。
対象外は理由を表示して自動再試行を停止し、再スキャンで旧プレイの証拠を補いません。
受付済みimport IDのGET確認は継続しますが、対象外ジョブの再POSTは行いません。

HLN→FORCE LNの許可はユーザーと合意したBMZ側の条件です。TachiのDirect Manualと
固定ノーツ数の検査を確認していますが、Kaleid全体の公式受入や本番デプロイとの一致は未確認です。
上流の根拠と差分は[main統合記録](../notes/2026/2026-11-13-kaleid-main-bokutachi.md)、
他IRとの違いは[Kaleid機能別IR条件](kaleid.md#機能別ir条件)を参照してください。

## PMSの入力機器とUPDATE SCORE

PMSは結果保存時にBMZが確定した入力機器区分を使います。
Controllerは`pms-controller`、Keyboardは`pms-keyboard`へ送信します。
物理寸法の自動判定、機種の許可リスト、専用の申告設定は追加していません。
**TachiのController部門はACサイズのコントローラーを前提としています。**
BMZの入力分類により送信先が決まる点を確認して利用してください。

UPDATE SCOREは、同じ譜面・LN区分・DOUBLE区分・ルール・入力機器の過去ローカル成績と比較します。
EX・ランプ・最大コンボは最大、BP・CBは最小を独立に集計し、いずれかの改善で送信します。
同じ入力機器の履歴がなければ初プレイとして送信します。KeyboardのBESTでControllerの初投稿を抑制しません。
比較に今回の履歴は含めません。ローカル全体のBESTや他IRの区分は変わりません。
比較元はBMZのローカルプレイ（`source_kind = Local`）に限定します。
beatoraja等の外部スコアは、DB取り込み・IRダウンロードのどちらでも比較元に含めません。
入力機器が不明な外部スコアの既定値Keyboardで、新しいKeyboardプレイを抑制しないためです。

新しいBokutachiアカウントに未投稿でも、同じ入力機器の過去ローカル成績を更新しなければ
UPDATE SCOREでは送信しません。ALWAYSとCOMPLETE SONGの意味は既存IRと同じです。
作成済みジョブの再試行時には、BEST更新判定や入力機器の判定をやり直しません。

## 譜面の照合

7K／14Kは元ファイルのSHA256でBokutachiの譜面を解決します。
PMSは公開ハッシュ検索から、入力機器区分・SHA256・CHART・primaryが一致する候補を選び、
候補のsong IDで再解決します。chart ID・game・SHA256・採点ノーツ数を再確認し、
送信本文でも同じ`tachiSongID`と`difficulty: "CHART"`を使用します。
Bokutachiが返す文字列のsong IDはそのまま使用し、旧形式の数値IDも読み取ります。
旧版で譜面照合が `invalid type: string … expected u64` で失敗した場合は、
修正版の送信キューから該当ジョブを個別に再送信すると、保存済みの成績で照合をやり直せます。

未登録、候補の曖昧さ、ハッシュや採点ノーツ数の不一致は理由を表示して停止します。
「採点ノーツ数不一致」は、本人の全曲分の採点対象数がBokutachiの登録数と異なるという意味です。
判定数の合計（空POORを含む）、途中まで通過した数、G-BATTLEの相手を含む表示用ノーツ数とは比較しません。
比率補正・ノーツ数の書き換え・別ハッシュへの置換・譜面の自動登録はしません。
後日登録・修正された場合は送信キューで該当ジョブを選び、個別に再送信すると再照会します。
対象外のジョブは一括同期・失敗分の一括再送では再照会しません。
送信キューのprovider選択でBokutachiを選びます。ランキング用primaryの指定は不要です。
「完了（登録成功・新規追加なし）」で終端結果や警告を確認できます。

## 受付と登録完了

1リクエストで1スコアを送ります。「受付」は登録完了ではありません。
受付後はimport IDを保存し、短いGET確認を繰り返します。再起動や通信失敗後も、そのIDの確認から再開します。
通常の通信失敗や処理中のジョブは、手動再試行でも既知のimport IDの確認から再開します。

- スコアIDが1件確認できた場合：登録成功。警告があれば保持して表示します。
- スコアIDがなくエラーがある場合：登録失敗。理由を保持します。
- スコアIDもエラーもない場合：「新規追加なし（重複等）」。新規追加を確認できなかった終端結果です。
  重複と断定するものではなく、新規成功にも数えません。自動再送しません。
- 応答の欠落・型不正・アカウント不一致：確認異常として停止します。成功扱いにはしません。

401／403はキーと権限の修正が必要です。429は待機時間を尊重し、同じoriginへのPOSTを待機させます。
通信失敗・408・5xxは既存の上限付きバックオフで再試行します。受付直後のpoll 404は120秒の猶予内で
GETを再試行し、継続する場合はimport IDを保持したまま自動確認を止めます。
Tachiがインポートの失敗を明示した場合も自動再POSTはしません。
送信キューでそのジョブを選び、個別に「再送信」すると、保存済みの内容・時刻で登録をやり直します。
元のAPIキーのアカウントを確認し、以前のimport IDを退役済みとして保存してから再送します。
再起動後に古い受付receiptが残っていても、退役済みIDへ戻りません。
この操作は、インポート処理の400系エラー、120秒後も続く「対象のインポートなし」、
既知のジョブ失敗を示す500応答に限ります。認証・権限エラー、408、429は含みません。
原因を判別できない500やプロキシ障害ではIDを保持し、GET確認を続けます。
一括同期・失敗分の一括再送では、失敗が確定したインポートも登録し直しません。
POSTの応答を受信できずimport IDが不明な場合は、保存した内容・時刻のまま再送します。
Tachiにないidempotencyヘッダーは使わず、必ず一度だけ登録されるとは保証しません。

## コース各曲の送信

コース各ステージは、その譜面の単曲スコアとしてDirect Manualへ送信します。
各曲に保存されたEX・判定内訳・BP・最大コンボ・プレイ時刻を使い、コース合計から分割しません。
ランプは原則`NO PLAY`です。FullCombo／Perfect／Maxだけ`FULL COMBO`になります。
コース全体をHARD等でクリアしても、各曲にHARDのランプは付きません。
通常単曲のNoPlayや有効な実プレイ結果がないものは、この例外に含みません。

7K／14K／9Kのルール、LN区分、元譜面、キー変換、実効アシスト、分岐の条件は通常単曲と同じです。
照合には各曲の全譜面分の採点ノーツ数を使い、コース総数や通過ノーツ数は使いません。
PMSの送信先は各ステージに保存された入力機器で決まります。最後の曲の機器や再送時の設定は参照しません。

各曲はALWAYS／COMPLETE SONG／UPDATE SCOREに従います。COMPLETE SONGはその曲の実際の完奏状態で判断し、
変換後のNO PLAYやコース全体の成否から判断しません。UPDATE SCOREは各指標の改善を独立に比較し、
PMSでは同じ入力機器の過去ローカル成績を使います。途中終了時のBP・CBも保存結果の値を保ちます。
後続曲で失敗しても、前の曲の送信は取り消しません。
未登録のオリジナルコースや3曲・5曲のコースでも、各譜面が条件を満たせば送れます。

## BMS段位の更新

登録済みBMS 7K／14Kの適格な4曲コースをクリアすると、段位更新を送信します。
各曲の単曲送信とは独立しています。単曲やコース合計の自己ベスト更新、各曲の送信成功は必要ありません。
UPDATE SCOREで各曲を送らなかった場合も、適格な新しいコースクリアで段位更新を行います。
取得済み段位より上かどうかはBokutachiが判断します。

すべてのステージが同じネイティブ7Kまたは14Kで、LR2oraja・保存済みLNのみの区分となり、
手動中断なく全4曲を完奏して段位ゲージ（CLASS／EXCLASS／EXHARDCLASS）でクリアしている必要があります。
実効アシスト、キー変換、譜面分岐などは対象外です。コースのIR公開設定も必要です。
Easy系やアシストありの結果をNormalに置き換えて送りません。
ゲージ自動切替で各曲の表示ゲージが異なる場合も、実際の持ち越し値からコース最終ゲージが全曲で残っていたことを確認します。

コース制約はそのまま対応するbeatoraja形式へ変換します。CN／HCN制約、
GAUGE_LR2以外のGAUGE制約がある場合は、採点がLNのみでも対象外です。
GAUGE_LR2という指定がなくても、実際のLR2orajaルールと段位ゲージが条件を満たせば対象になります。

配置は全曲を確認し、単一の正確な値として表せる場合だけ送ります。
現行Tachi APIは`1P配置 + 10 × 2P配置 + 100 × DPオプション`の全体が0または1であることを要求します。
正規と、コース制約が許す1PのみMIRRORに対応します。**14Kの2P MIRROR・両側MIRROR・FLIPは段位更新の対象外です。**
RANDOM、F-RANDOM、MF-RANDOMや、曲ごとに異なる配置を正規へ丸めません。
この制限で段位更新できなくても、各曲の単曲スコアは通常の条件と配置変換で送信できます。

実際にプレイした4曲のMD5を曲順どおりに`POST /ir/beatoraja/submit-course`へ送り、
段位系列・段位値への変換はTachiの対応表に任せます。タイトルやBMZのコースハッシュから推測しません。
互換ヘッダーは`X-TachiIR-Version: v4`です。クライアント名の偽装やDirect Manualのclassesは使いません。
MD5・曲順・制約・LN・実効ルール・ゲージ・クリア・配置・送信先を結果確定時に固定します。
再起動後も保存した要求を再送し、変更後の設定・ライブラリ・コース定義は参照しません。

段位APIは同期応答です。単曲のimport ID・202・pollは使いません。
結果画面と送信キューでは「段位更新」として、次を区別します。

- 更新完了：サーバーが段位の更新を確認しました。
- 確認完了（変更なし）：同等以上を取得済みなどで変更がありません。
- 段位未更新：サーバーがクリアとして受理しませんでした。新規獲得とは表示しません。
- 対象外：対応表にないコース（404）や、旧ジョブに保存された不適格な要求です。
- 失敗：条件違反・不正応答・認証問題等の理由を表示します。通信失敗・429・5xxは再試行します。

対象外や恒久的な条件違反は自動再送しません。スコアID・合計EXの登録結果・コースランキングは作りません。
新しいコース結果がローカルで明らかに条件を満たさない場合は、理由をログへ記録して段位ジョブを作成しません。
9K、4曲以外、未クリア、IR非公開などのコースで送信キューを埋めません。各曲の送信判定は独立しています。
**9Kは各ステージの単曲送信までの対応です。** コース全体の自動段位更新は行いません。

## 譜面別ランキング

PrimaryにBokutachiを選ぶと、選曲と単曲リザルトに7K／14K／9Kの全体ランキングを最大100件表示します。
設定済みアカウントの自己ベスト順位は、表示範囲外でも個別に取得します。
譜面のSHA256で照合し、Bokutachiが返す順位・参加人数・EXスコア・ランプを表示します。
BPと最大コンボはAPIが返す値を使い、欠損時は表示上0になります。
表示する順位はBokutachiの部門内の順位です。BMZのLN区分・ルール・DOUBLE区分による絞り込みは行いません。

PMSの選曲、オートプレイ、リプレイのリザルトは、1Pにコントローラーが割り当てられていればController部門、
それ以外はKeyboard部門を表示します。保存済みプレイのリザルトはそのプレイの入力機器を使います。
リザルトは現在の順位を取得し、今回分の登録成功を確認した時点で再取得します。
Primaryは明示して選びます。「IRページを開く」はBokutachiのトップページへ案内します。

## 対象外の機能

過去ローカル単曲・コース履歴の一括送信、任意コースの合計EX・BP・ランプ・PBの登録、
コースランキング・ライバル比較、PMSコース全体の段位更新、Direct Manualのclassesによる段位更新、ライバル・リプレイ・
G-BATTLE対戦データの取得、リプレイアップロード、attestationは未対応です。
「新規プレイのみ」は過去履歴から送信ジョブを新しく作らないという意味です。
新規プレイから作成済みのジョブは、日をまたいだ再試行でも処理します。

## 保存データと実装

組み込み4枠目へBokutachiを追加し、既存カスタム設定は後続へ移します。既存provider key、認証情報、primaryは保持します。
新しいBokutachiジョブの専用contextに、元モード・本人の採点モード・キー変換・採点範囲・送信先game・originを固定します。
旧payloadの欠けた情報は推測しません。他IRのpayloadや既存リプレイは変更しません。
単曲context v1は引き続き処理します。v2では通常単曲とコースステージを明示し、元のステージ結果と完奏状態を保存します。
段位は既存のCourseジョブに専用のversion付き要求を保存し、進捗・終端結果はoutboxへ保持します。
段位未更新は`not_cleared`として保存し、変更なしの`no_change`と区別します。
結果画面と送信キューは保存状態を表示し、診断メッセージの英語表現で結果を判定しません。
今回のコース対応による追加DB migrationはありません。必要な実プレイ情報のない旧Courseジョブは推測して送りません。

network DB v7は、固定した送信本文・解決済み外部ID・import ID・段階を既存ジョブとは別のテーブルへ保存します。
次回時刻・診断は既存outboxへ保存します。APIキーを含まない受付receiptもローカルへ保存し、受付後のDB書込み失敗からの復旧に使います。
