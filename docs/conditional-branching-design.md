# 動的条件分岐のチャンネル・実行順・ノーツ数設計

2026-09-19時点の設計メモ。実装済みの仕様と対応範囲は [conditional-branching.md](conditional-branching.md) を参照。以下には実装前の提案・確認候補も含む。
参照: `.local/KaleidBeat/documents/format-header.html` のCONDITIONAL仕様、BMZ `b44b9cb9`。
全体計画から動的条件分岐の具体化を独立して記録する。

## 1. ユーザー方針と提案の区別

ユーザーから示された方針:

- 分岐で変更できるチャンネルは原則すべてを目指す。
- 事前のノーツ数集計はDEFAULTを使用する。
- リザルトのトータルノーツは実際のノーツ数を使用する。
- 判定は、評価時刻の直前までの確定状態で分岐を決め、その後に同時刻のイベントを処理する順序を採用する。
- 音声は実装の簡潔さを優先し、分岐境界で旧枝の音が多少混ざることを許容する。予約済み・再生中の音を分岐のために取り消さない。

実行順序と音声の扱いは上記のBMZ方針として確定する。Kaleidの実際の境界挙動まで確認済みという意味ではない。
評価時刻ちょうど/直後の切替について厳密な音声一致は求めず、これを管理人への確認待ちや追加の予約制御を導入する理由にしない。
以下でBMZ案と記したその他の適用範囲・集計規則は提案段階。互換性を求める未確定箇所は管理人へ確認する。
「すべて」は各チャンネルの本来の意味をBMZが実装していることを前提とする。A6等の未対応機能は、分岐対応とは別に機能本体の実装が必要。

## 2. 基本方針: チャンネルより、変更する範囲を制限する

BPM/STOPを分岐対象にすること自体に原理的な問題はない。分岐点までの時刻・採択履歴・判定結果は確定した履歴として保持し、未確定の未来だけを更新する。
音声出力は別扱いとし、未来の発音でも既に予約済みなら旧枝の予約をそのまま残す。

| 種類 | 例 | 変更時に必要な扱い |
| --- | --- | --- |
| ノーツ/区間 | 1x〜6x、Mine、Potion、Dummy、FreeZone | 未判定の未来を変更。判定済みノーツや保持開始済みLNの端点を書き換えない |
| 視覚/状態 | BGA、TEXT、SCROLL、SPEED、ST、色/不透明度 | 分岐時刻から切替。前枝のイベントを除去し、既に表示中の状態を継続するか変更するかを明示 |
| 音声 | 01/BGM、キー音、97/98音量 | 予約済み・再生中の音は維持。分岐確定後に予約するイベントから採択枝を使う。既存の音量/再生制御は維持 |
| 判定幅 | A0/EXRANK | 判定済み結果を変更せず、受付中ノーツへの新しい判定窓の適用規則を決める |
| 時間軸 | 03/08のBPM、09のSTOP | 分岐点から後のTimingMap、ノーツ/BGM/BGA時刻、次の分岐時刻を再計算 |
| 小節構造 | 02の小節長 | 原則、まだ始まっていない小節だけを変更。現在/過去の小節を変更すると分岐点自身も動く |
| オプション | A6等 | 効果ごとに範囲を決める。配置/LN種別/ゲージ等を変えるものを単なる表示切替として扱わない |

`#WAVxx`、`#BMPxx`、`#BPMxx`、`#STOPxx`、`#BASE`、`#LNMODE`、`#TOTAL` 等はチャンネルとは別の定義/ヘッダ。
「全チャンネル可」から「全ヘッダを実行中に書き換え可」は導かない。枝内のリソース定義を許可する場合はロード時に枝ごとに解決し、異なる枝の同一IDが相互に上書きしない内部IDを割り当てる。
BASEや鍵盤数など、パースや入力構造を決める設定を実行中に変更することは、この方針に含めない。

## 3. BPM / STOP / 小節長

### BPM

例: 分岐点の到達時刻が10.000秒で、採択枝がBPM120→240に変更する場合。

- 分岐点そのものは10.000秒に固定する。
- そこから1拍先のノーツは、10.500秒ではなく10.250秒になる。
- その先のBGM/BGA、LN終端、判定期限、後続の分岐時刻、曲終了時刻も新しい時間軸から求める。
- ただし、既に予約した音の発音時刻は変更しない。分岐境界で旧時刻の音が残ることは許容する。
- BPM変更より前に鳴り始めたPCMを自動で倍速にしない。長いBGMが譜面とずれる場合、それはBMSのBPM変更でも起きる音源配置上の問題なので、分岐だけにタイムストレッチを導入しない。

BMZは現在、取り込み時に各イベントへ `TimeUs` を付けており、BPM値だけ変更しても同期しない。
未確定イベントは小節内位置/有理数位置を正として保持し、採択後に未来部分の時刻を導出する。
正で有限のBPMを条件に時間の単調性を維持する。負/ゼロBPMや負STOPによる時間逆行は、この設計の対象にしない。

### STOP

同位置のBPMとSTOPは、現在の `bmz-chart/src/timing.rs` と同じ **BPM→STOP** をBMZ案とする。
BPM120→240と `#STOP01 192` が同位置にあれば、新BPMでSTOPを計算して1秒になる。
その位置の通常ノーツは到達時刻に置き、STOPは後続位置への移動を遅らせる。キー入力・音声処理そのものを停止しない。
STOP中にtickが同じ値を返しても、採択済みのConditionalIdを再評価しない。

### 小節長02

例えば `#CONDITIONAL 65.5` で65小節の長さを変更すると、「65小節の50%」の時刻まで変わる。
分岐評価の結果でその評価時刻自身を再計算すると、過去へ移動したり、評価し直しになったりする。

BMZ案:

- 65.5で変更できるのは66小節以降の長さ。
- 65.0の入場前評価なら65小節の長さも変更可能。65.0の到達時刻は先行小節で既に決まっているため循環しない。
- 未来の小節長変更は、その中の全イベントと後続小節、後続分岐の位置/時刻へ反映する。
- 既に一部が早押し判定された未来の小節を含む場合は、次節の確定済み履歴保護も必要。

## 4. 通常ノーツにもある「未来だけなら安全」と言い切れない場合

### 早押し判定

分岐点が10.000秒、ノーツ時刻が10.050秒でも、そのノーツが9.950秒の入力で判定済みの場合がある。
10.000秒でノーツを差し替えると、スコア/ゲージ/キー音を巻き戻すことになる。
同様に、保持中LNの終端だけを削除・移動すると保持状態が壊れる。

BMZ案では以下を契約にする。

- 判定済みオブジェクトと、判定処理を開始したLNペアは固定する。
- 枝がそれらを書き換えようとする場合は、互換仕様で明示された扱いがない限り不正な分岐として診断する。黙ってスコアを消したり再判定したりしない。
- 作譜上の確実な条件は「差し替え対象が最も早く判定され得る時刻より前に枝を確定する」こと。音声準備時間と同じく、適用開始位置の問題として扱う。
- 分岐未確定のDEFAULTを早押し判定対象にするかどうかも、Kaleidへの確認が必要。

### 音声の先行出力: 予約済みの音は維持する

現在の `AUDIO_SCHEDULE_AHEAD_US` は100msで、BGMと自動キー音を先行予約する。
10.000秒で枝を決めても、10.050秒の旧枝BGMが既に予約されている可能性がある。
ユーザー方針に従い、その旧枝BGMは予約時のまま再生してよい。再生中の音も分岐を理由に停止しない。

実装方針:

1. 音源は全枝を事前ロードする。分岐時には音源読込や合成を行わない。
2. 通常の先行予約を維持する。分岐点の手前で予約を止めたり、専用の待ち時間を入れたりしない。
3. 分岐時は採択したイベント列へ切り替える。未予約の音は評価時刻T以降の新枝から予約し、Tより前の新枝イベントをさかのぼって鳴らさない。
4. 既に予約済みの旧枝イベントは、gameplay側のpending queue、audio側のqueue、再生中voiceのいずれにあってもそのまま残す。分岐専用のcancel/revision判定やPCMの巻き戻しは追加しない。
5. 共通部分のイベントは安定ID等で予約済み状態を引き継ぎ、cursorを戻したために同じ共通BGMを二重予約することは防ぐ。旧枝と新枝の異なる音が境界で重なることは許容する。

例: T=10.000秒で切り替え、旧枝の10.050秒の音Aを予約済みならAは残す。新枝の10.050秒に別の音BがあればBも通常どおり予約し、AとBの重なりを許容する。
100msは通常速度での現在の先行予約幅であり、混ざる音の継続時間の上限ではない。予約済みの長い音はその後も再生される。
実際に予約済みとなる範囲は更新周期等で変わり得るため、境界音の厳密な一致はリプレイ/動画出力でも保証しない。分岐採択・判定・ゲージ・スコアの再現は維持する。
旧枝の音が残ることを理由に旧枝のノーツを判定へ残したり、リザルトの実ノーツ数へ加算したりはしない。

## 5. 採用する同時刻処理

問題例: コンボ99で、時刻Tに通常ノーツの入力と `WHEN COMBO>=100` の分岐評価がある。
入力→評価ならtrue、評価→入力ならfalseになる。新枝がその通常ノーツ自身を変更できる場合は循環も起きる。

ユーザー承認により、**Tの直前までの確定状態で枝を決め、その後Tのイベントを処理する** 順序を採用する。

1. 時刻 `< T` の入力、判定、見逃し、ゲージ更新を時刻順に完了する。Tまでの物理的な時間進行と、時刻Tに起きる離散イベントを区別する。
2. SCORE/COMBO/MISS/GAUGE等のスナップショットを固定し、時刻Tの全CONDITIONALが同じ状態を参照する。各ブロック内では記述順で最初のtrueを採用する。
3. 採択した変更をまとめて適用する。同位置の競合はチャンネルごとの通常規則を使う。BGMの重ね配置まで一律後勝ちにしない。解決が必要な上書きの優先順位は原文順等で固定する。
4. 時刻TのBPM→STOP、判定窓/表示/音量等を反映し、時刻Tの入力・ノーツ・ゲージイベントを処理する。その結果を時刻Tの分岐へ戻さない。

この順序ではCOMBO99の例はfalse。同時刻のポーション回復や地雷ダメージも、その時刻の分岐のGAUGEへは含めない。
同一時刻に複数分岐があっても、先の枝の副作用を次の枝の条件へ流さない。次の時刻の分岐は更新済み状態を見る。

通常入力同士、Mine/Potion、HCN更新、閉店の細かい同時刻順序も仕様化する必要があるが、それを分岐の評価順と混ぜない。
入力遅延補正によって後から届いた過去timestamp入力の締切も必要。枝確定後に無制限の巻き戻しを認める設計にはしない。
同じ入力記録で再現できるよう、ライブ実行・リプレイ・動画出力で同じ順序を使い、採択枝は記録して再生時に優先する。

現状の `advance_session_frame` はBGM予約、入力、通過処理、見逃し、ゲージ更新等をまとめて処理する。
分岐時刻をまたいだ1更新をこの順で一括処理すると、Tより後の入力結果がTの条件へ混ざるため、Tで処理区間を分割する変更が必要。

## 6. ノーツ数の分離

| 用途 | 方針 | 確度 |
| --- | --- | --- |
| 選曲表示・library DB・事前密度 | DEFAULT譜面の数 | ユーザー方針 |
| TOTAL自動計算・通常判定によるゲージ回復係数 | DEFAULT基準でプレイ開始時に固定 | Kaleid文書に基づくBMZ案 |
| 分岐条件RATEの全曲理論値 | DEFAULT由来を維持。進行分母か全曲分母かはKaleidへ確認 | 未確定 |
| リザルトのトータルノーツ | 採択枝を反映した実際の採点対象数 | ユーザー方針 |
| リザルトの理論EX/EX率 | 実際の採点対象数×2を分母にする | 表示整合性のためのBMZ提案 |

「実際」は押せた個数ではなく、選ばれた譜面に存在する採点対象数。見逃したノーツも含む。
非採択枝、地雷、ポーション、ダミー、空POORはこの数へ含めない。
実際に適用したLN policyに従い、Tap/LN/HLNは1、CN/HCNは始点と終点で2とする。
構造上のLN本数と採点対象数も区別する。

例: DEFAULTが1000ノーツ、採択後の譜面が800ノーツで、全てPGREATだった場合。

- 選曲時は1000、TOTAL/ゲージ係数もDEFAULT基準。
- リザルトは800、実EXは1600。
- 提案するリザルトEX率は1600 / (800×2) = 100%。分岐条件RATEがDEFAULT全曲分母なら、その内部値は80%。両方を同じフィールドで兼用しない。
- 非採択枝に由来する200ノーツを未処理POORとして足さない。

実装では `reference_total_notes`、`resolved_total_notes`、`judged_notes` を分ける案とする。
FC/Perfect/Maxの判定、結果BPの未処理補完、ghost、score DB、最大EXの検証も対応させる。リザルトの表示だけ差し替える変更では足りない。
ベストEXを枝をまたいで単純比較するか、RATE/枝別に比較するかは別のランキング方針として残す。

途中FAILED/終了では未来の枝がまだ選ばれておらず、全曲の実際の採点対象数を確定できない場合がある。
その場合は「確定部分の数」と「未確定あり」を保存する案とする。DEFAULTで残りを補った見積もりを持つ場合も、確定した実数とは別フィールドにする。
未評価枝をDEFAULTで固定して全曲の結果数を出す仕様にするかは、完走時の方針とは別に決定する。

## 7. 管理人へ優先して確認する内容

1. 03/08/09/02を枝に置いた場合、後続時刻を再計算するか。評価中の小節長変更を許可するか。
2. 分岐前に早押し判定済みのノーツ、保持中LNを差し替えたときの動作。
3. A0変更時の受付中ノーツ、音量/表示状態の引継ぎ、枝内リソース定義のスコープ。
4. RATEの分母と、リザルトを実ノーツ数にする場合のEX率・途中終了・ベスト比較の扱い。

同時刻の分岐評価順と境界音声の厳密な挙動は、BMZ方針が決まったため実装前の必須確認項目から外す。

## 8. 受入テスト

- COMBO99→100、GAUGE閾値前後、ポーション/地雷と分岐が同時刻の例。
- 同tickの複数分岐とBPM/STOP、STOP中の分岐再実行防止、長い1更新で複数分岐を通過する例。
- BPM120→240で1拍先が0.5秒から0.25秒へ変わり、予約済み音を除く未来イベントが同期する例。
- 65.0で65小節長変更が可能、65.5で65小節長を変えるケースは診断される例。
- 早押し済み未来ノーツ、保持中LNの終端の保護。
- 予約済み/再生中の旧枝BGMは残り、未予約の旧枝BGMは切替後に予約されないこと。共通BGMの二重予約と新枝の過去イベントの再生が起きないこと。
- 境界で旧枝と新枝の音が重なっても、旧枝の判定/ノーツ数が復活しないこと。
- DEFAULT1000/実800・実1200、LN種別混在、非採択枝をPOORへ加算しない例、途中終了。
- 異なる更新頻度で同じ入力列を再生し、採択・ゲージ・判定・リザルトが一致すること。旧枝音が残る範囲の差は許容し、音声には上記の予約方針を検証する。

実装と自動テストを追加済み。確定済みノーツの保護、途中終了のDEFAULT確定、対応モードなど、実際に採用した判断は実装仕様書を正とする。
