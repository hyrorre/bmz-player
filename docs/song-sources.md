# 曲の取得元とスキャン

曲rootには通常の譜面ファイルとZIP / RAR / 7z / tar.gz / LZHを置けます。書庫を置いたフォルダを設定の
曲rootへ追加してスキャンするか、`bmz-player songs load <folder>`で登録し、Selectで譜面を選択します。
書庫内のBMS / BME / BML / PMS / BMSONを登録し、音声・BGA・曲画像・プレビューは利用時に展開します。
暗号化書庫や安全性・資源量の制限を超える書庫はエラーとして扱います。
再生コマンド、メディアキャッシュ、対応圧縮方式と上限は[書庫内譜面の直接再生](archive-songs.md)を参照してください。

BMSONは小節境界の補完を含めて最大10,000小節まで読み込みます。明示された小節線の件数や、
標準小節長で換算した最終pulseが上限を超える譜面は読み込み失敗として記録し、ほかの譜面のスキャンを続けます。

## 自動取得の接続先とプロキシ

[HTTP/IPFSの譜面取得](chart-downloads.md)では、API応答のURLとリダイレクト先を含め、
各リクエストの前にIPリテラルまたはDNS応答を検査します。公開先から始まる取得では、
ローカルアドレスを1つでも含む宛先と、localhost・そのサブドメイン・`.local`のhost名を拒否します。
末尾ドット付きのhost名も同じ規則で判定します。設定した最初のHTTP/IPFS APIが
ローカルアドレスだけを指す場合は、ローカルAPIとして利用できます。

リダイレクトは最大10回で、公開先同士の移動を許可します。直接接続では接続時にもDNS応答を検査し、
事前確認後のDNS rebindingによるローカルへの接続を防ぎます。
OS設定や環境変数に指定されたプロキシの自動利用も維持します。

プロキシ経由でもクライアント側で事前に名前解決しますが、実際の接続先はプロキシが名前解決します。
クライアント側で名前解決に失敗した場合や応答が空の場合は、事前検査を保留して通信を試みます。
この場合、最初の接続先をローカルとみなす例外は有効にしません。
直接接続では接続時に再解決して検査し、解決できなければ接続に失敗します。
プロキシだけが名前解決できる環境や、split-horizon DNSなどで結果がクライアントと異なる環境では、
クライアントの検査をすり抜け、プロキシがローカルアドレスへ接続するリスクが残ります。
この検査はプロキシ側のDNSや接続制御を保証するものではありません。

IPv4の`192.0.0.0/24`・`198.18.0.0/15`・`240.0.0.0/4`も拒否対象です。
IPv4-mapped IPv6、NAT64の`64:ff9b::/96`、6to4の`2002::/16`は、内包するIPv4にも同じ検査を適用します。

## 安定したパスと譜面identity

DBの取得元は`C:/BMS/pack.zip!/folder/song.bms`の形式で保存します。`!/`より前は元の書庫、
後ろは内部entryです。譜面pathを受ける既存CLI引数にもこの形式を指定できます。
書庫本体だけを譜面として指定した場合は、スキャン登録または内部譜面の指定を案内します。

譜面のSHA-256とMD5は内部entryの元bytesから計算します。ファイル名、展開先、文字コード変換、
RANDOM分岐によって変化しません。Score / Replay / Practiceの譜面hashとの対応は通常ファイルと共通です。
同じ譜面が複数の書庫や通常フォルダにある場合は各コピーを登録し、選択したコピーの音声や画像を使います。
そのコピーが利用できなければ、有効な曲root内にある同じhashのコピーへフォールバックします。

通常の一覧には最後の成功した登録を使い、ディスクを読みに行きません。実ファイルの利用可否確認は
元の書庫とentryの存在で判定し、開始前の検証では元譜面bytesのhashを照合します。
cacheの有無は所持判定に影響しません。元譜面が変更された場合は再スキャンが必要です。

## 走査と更新

beatorajaと同じく、隠し属性やドットで始まる名前のファイル・フォルダも探索します。
OSの属性は読まず、次の名前だけを、どのOSでも、通常のファイル・フォルダと書庫内の両方で常に除外します。

- macOSのAppleDouble（`._*`）と、書庫ツールのメタデータ用フォルダ（`__MACOSX`）
- ドライブを曲rootにした場合のごみ箱とシステム用フォルダ（`$RECYCLE.BIN`、`System Volume Information`、
  `.Trashes`、`.Trash`、`.Trash-<uid>`）

ごみ箱には削除した譜面が拡張子を保ったまま残り、システム用フォルダは読み取りが拒否されて
rootの削除判定を止めてしまうためです。除外した名前の下にある既存の登録は、次のスキャンで取り除きます。
Everythingによる探索も同じ名前の規則だけを使い、ファイルごとの属性の確認は行いません。

rootの有効・無効および再帰設定は、書庫本体の位置を基準にします。再帰を無効にしたrootでも、
直下の書庫内にあるサブフォルダの譜面を列挙します。書庫内でも上の名前の規則だけで除外します。
Everythingによる発見でも同じ書庫一覧化を使い、利用できない場合は通常の走査へ戻ります。
読み取れない書庫は通常の走査と同じく個別のissueとして記録し、root全体の発見は失敗させません。

アプリを起動したまま繰り返すスキャンでは、書庫ごとに譜面entryの名前・サイズ・同じフォルダの`.txt`の有無と
書庫世代だけをメモリに保持します。書庫のサイズ・更新日時・作成日時（Unixではinodeとctimeも）が
変わらない間は書庫を開き直さず、変わった書庫だけ索引を読み直します。保持するのは16,384書庫・
合計262,144譜面までで、超えた時点で保持分を捨て、以降の書庫を読み直して保持し直します。
音声・画像を含む書庫全体の索引は、再生・選曲用に直近の32書庫（合計100,000 entryまで）だけを保持します。
CLIの`songs load`は毎回新しいプロセスのため、この保持の効果はありません。

通常の走査は、同じ階層のフォルダを並列に読み、譜面のサイズと更新日時を取得します。
種別はフォルダ一覧の情報で判定し、キー音などの素材にはフルパスを作りません。
新規・変更された譜面は1件ずつ並列に解析し、解析を終えた順に256件を1トランザクションで書き込みます。
重い譜面があっても他のスレッドは次の譜面へ進みます。解析と書き込みは並行し、解析結果の受け渡しは
書き込み中の1バッチと、受け渡し待ちの256件に制限します。
同じサイズの解析候補が複数見つかった場合、読み取った内容のSHA-256と解析形式が一致する譜面は、
同じスキャン内で、ルートや書庫をまたいで譜面情報・統計・警告を再利用できます。
このキャッシュには件数と保持データ量の上限があります。登録パスとプレビューは譜面ごとに処理します。
通常ファイルの密度・主BPMなどの統計と保存形式への変換も解析ワーカーで行います。
密度分布・速度変化・レーン別集計は、小さくなる場合にDEFLATEで圧縮して保存します。
既存のテキスト形式はそのまま読み、譜面を取り込むときに新形式へ更新します。
圧縮済みのDBを旧版へ戻す場合は、更新前のDBを復元するか、旧版で譜面を再読み込みしてください。
再解析結果と保存済みの統計が同じ場合は、必要なバージョン更新と音量解析の無効化だけを行います。
内容と順序が同じ警告は、既存の記録時刻を保持します。
CLIの`Timing`にある`analysis_worker`と`encode_worker`は各ワーカーで測った経過時間の合計です。
`commit`は通常ファイルのバッチのコミット時間で、`write`に含まれます。`batch_wait`は通常ファイルの
バッチに必要な解析結果が届くまで書き込み側が待った時間、`reused`は解析結果を再利用した登録件数です。
スキャンでは、譜面が参照する音声・BGAのファイルを探しません（`AssetLookup::Declared`）。
宣言されたパスのまま解析し、別拡張子への解決や存在確認は再生時に行います。
プレビュー音声は一覧に表示するためスキャン時に解決しますが、フォルダ内の名前で`preview*`の候補を
絞ってからファイルを確認します。通常ファイルでは、明示された`#PREVIEW`を先に解決し、
同じ曲フォルダにある`preview*`の探索結果をその走査中に共有します。候補がなかった場合も共有します。

solid書庫の譜面は1回の展開走査でまとめて読み取り、書庫ごとのDBトランザクションで反映します。
譜面以外の素材はスキャン中にcacheへ展開しません。書庫の内容が変わっていなければ登録済み譜面を
再解析しません。素材だけの変更も書庫世代が変わるため再反映します。

正常に列挙・読み取りできたスキャンでのみ、削除された内部entryや元書庫の登録を取り除きます。
書庫が破損・読み取り不能、または展開途中でCRC不一致になった場合は既存登録を保持し、そのrootの
削除判定を見送ります。暗号化・分割・自己解凍形式・未対応の圧縮方式など、形式として認識したうえで
対応していない書庫は、何度読んでも譜面を得られないためissueとして記録するだけで、削除判定を止めません。
署名を認識できない書庫は、破損と区別できないため従来どおり削除判定を見送ります。
再走査で書庫が復旧すれば再び更新します。通常の譜面parseエラーは個別に記録し、
譜面のサイズ・更新日時か`CHART_IMPORT_VERSION`が変わるまで再解析しません。
同じ内容は毎回同じ理由で失敗するためで、2回目以降のスキャンでは変更なしとして数えます。
ファイルの読み取りエラーは一時的な場合があるため、次のスキャンで再試行します。
書庫内の譜面のparseエラーはその世代の結果として記録し、書庫か`CHART_IMPORT_VERSION`が
変わったときに再試行します（変化のない書庫を毎回全体復号しないため）。

`library.db`のmigration 35は書庫の取り込み済み世代を記録する`song_archive_scans`テーブルを追加します。
migration 36の`song_archive_fingerprints`は書庫全体のhashをファイル情報と組で記録し、
変化のない書庫の再hashを省きます。行を失っても次回に再計算するだけです。
migration 37は`chart_files.failed_import_version`列（既定値0）を追加し、parseに失敗した
`CHART_IMPORT_VERSION`を記録します。既存の失敗行は0のため、移行後の最初のスキャンで1回だけ再解析します。
既存charts・chart_filesのpathやscoreデータに破壊的変更はありません。

### シンボリックリンク

「シンボリックリンクを辿る」がONのときは、Unixのsymlink、Windowsのdirectory symlinkとjunctionを
同じ規則で辿ります。OFFのときはリンクを無視します。フォルダは実体のパス（canonical path）で識別し、
実体を取得するのはrootとリンクだけです。通常のサブフォルダの実体は親の実体から求めます。

走査は段階に分けて行います。各段階で、フォルダを並列に読みながらリンクを集めるだけにし、
段階の終わりに次の順で1つずつ採用します。採用したリンク先が次の段階で読むフォルダになります。

- 浅いリンクを先に、同じ深さならパスの順に判定します。並列処理の進み方や`read_dir`の列挙順には依存せず、
  同じ構成と設定なら毎回同じパスを選びます。
- リンク先がroot内、または採用済みのリンク先の中にある場合は辿りません。rootの実フォルダからのパスを優先し、
  同じリンク先を指す複数のリンクでは最初の1つだけを使います。
- リンク先がrootを含む（rootの祖先を指す）場合は辿りません。
- リンク先が採用済みのリンク先を含む場合は採用し、含まれる側のフォルダはそちらのパスで読みます。

各フォルダは1回だけ読まれ、循環するリンクがあっても走査は終わります。譜面や書庫を指すファイルのリンクは、
リンク先がフォルダ経由または先のリンクで読まれていなければ登録します。再帰を無効にしたrootでは、
フォルダのリンクは辿らず、直下のファイルのリンクだけを読みます。

リンク先が存在しないリンクや、リンク同士で循環して解決できないリンクは、譜面を含み得ないので
debugログを出して読み飛ばし、走査は完了扱いのままにします。リンク先へのアクセス拒否など、
譜面を見落とすおそれのある失敗はissueとして記録し、そのrootの削除判定を見送ります。

### 削除判定

削除判定は、rootの走査が完了したときだけ、DBへの書き込みを終えた後に行います。

- 通常の走査では、走査で見つからなかった登録をrootの範囲外として取り除きます。
  選ばれなかったリンク経由の別名や、リンクを辿らない設定でのリンク経由の登録、除外する名前の下の登録が対象です。
- 複数rootはすべての探索と書き込みの後に削除判定を行い、他のrootでも発見されたパスを保持します。
  未走査・無効・読み取り不能な別rootに含まれる登録は、そのrootの状態が不明なため削除しません。
- 今回のスキャンでいずれかのrootが見つけた登録は、存在するものとして保持し、もう一度確認しません。
  走査の後に消えた譜面は次のスキャンで取り除きます。取り込みの前に消えた新しい譜面は失敗として記録しません。
- 見つからなかった登録のうちファイルの確認が必要なもの（別rootに含まれる登録やEverythingの結果）は、
  譜面ファイルだけを並列に確認します。存在しないと確定したときだけ削除し、アクセスエラーでは保持します。
- 書庫の一覧・取り込み・削除の直前に同じ書庫世代であることを確認します。ファイル情報（サイズ・更新日時など）が
  変わっていなければ記録済みの世代を使い、書庫を読み直しません。途中で世代が変わったり
  確認できなくなったりした場合は、そのrootの削除と走査完了時刻の更新を見送り、次回の走査で再試行します。
  書庫自体の消失が確認できた場合は、その登録を取り除きます。
- Everythingの結果はファイルシステムより遅れることがあるため、Everythingで走査したrootでは
  結果に含まれない登録を範囲外とみなさず、ファイルと書庫の世代を確認してから削除します。

取り除いた登録と同じハッシュの登録が残る場合は、`first_seen_at`の早い方を引き継ぎます。
移動したりリンクの選択が変わったりした譜面も、新着として扱い直しません。スコア・プレー記録・お気に入り・
コースはハッシュで結び付いているため、パスの登録を取り除いても失われません。

## 展開cacheと素材の境界

展開先は実アプリの`AppPaths.cache_dir`（`BMZ_CACHE_DIR`指定対応）から明示的に渡します。
DBを開いた時点や譜面metadataの読み取りだけでは、ユーザーのcacheディレクトリへ書き込みません。
テストは個別の一時ディレクトリを使います。cacheを削除しても次の利用時に元書庫から再生成できます。
この機能では自動GCを行いません。使用中のcacheの手動削除は再生終了後に行ってください。

書庫の世代ごとに素材を分離し、元の書庫とentryのlocatorをDBへ保存します。
cacheの実パスを永続的な譜面identityとして使いません。元書庫を更新した場合は新しい世代を展開し、
古い世代の読み取り結果が新しい要求へ混ざらないようにします。

内部entryと譜面由来のWAV / BMP / STAGEFILE / BACKBMP / BANNER / PREVIEWは書庫root内に限定します。
`sub/song.bms`から`../shared/key.wav`へ参照する構成は使えます。絶対パス、root外への`../`、
代替データストリーム、cache内のリンク経由で外へ出る参照は拒否します。元譜面bytesを書き換える補正は行いません。
