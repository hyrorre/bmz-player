# Windows ポータブル版の旧更新ファイル整理

## 2026-11-24 初版

現在の版と一致する新配置のポータブル版が共有ロックを取得する前に、旧更新ファイルを整理する。
新配置の更新ロックと起動ロックを取れた場合に、新旧の未完了記録と旧パッケージの有無を確認する。
旧ロック2件は Windows の共有を許可せずに開き、空の通常ファイルだと確認してから削除を予約する。
旧バックアップの処理は両方の旧ロックを確認した後に行う。結果記録のある作業フォルダを
`updater/legacy-backups/` に移し、同じ名前の退避先や未完の作業は元の場所に残す。
更新ヘルパーが再起動直後もファイルを使用中なら、次の起動で再試行する。

## 2026-11-25 並行起動の修正

初版の整理が専用の更新ロックと起動ロックを排他取得するため、同時に起動した本体や
更新ヘルパーが更新中と判定して終了する経路があった。通常の起動用共有ロックを保持して整理し、
適用・復旧との排他に使う。整理だけのためのバイト範囲ロックは取得しない。
旧ロックは両方の属性を確認してから短時間だけ排他的に開く。起動側と更新ヘルパー側は、
旧ロックを開く際に共有違反や削除待ちがあれば最大500msの間再試行する。

旧パッケージや未完了記録、移動可能な作業フォルダの有無を整理前に確認する。
旧ロックが読み取り専用の場合は保護し、理由を起動時に記録する。
片方の削除予約に失敗した場合は、先に予約したファイルの削除を同じハンドルで取り消す。
バックアップは上書きを許可しない Windows の移動処理を使う。

- Windows 11 上で公式 v0.5.4 のヘルパーから検証用 v0.5.5 に更新した。自動再起動での整理、
  バックアップとログの保持、使用中・復旧待ちでの見送りと再試行を再確認した。
- 更新済みの検証用配置で CLI を2つずつ12組並行起動し、すべて成功した。
  読み取り専用の旧ロックがある場合は、CLI が起動して警告を出し、両方のファイルを保持した。
- `bmz-updater` の39テストが成功した。短時間の旧ハンドル競合、アプリの起動と更新準備、
  削除予約の取り消し、退避先の競合、旧配置のマーカー、別バージョン、Setup 用メタデータ、
  読み取り専用・空でないファイル、reparse point を確認した。
- `cargo fmt --check`、workspace の `check` と全ターゲットの Clippy、
  `cargo test --workspace --locked --no-fail-fast -j 1` が成功した。
  初回の全テストは Windows のページファイル不足でビルドが中断したため、ビルドの並列数を1にして再実行した。
  更新の確認範囲は Windows 11 のローカルディスク上のポータブル版。
  公開フィードからの取得、SMB 共有、Windows 8.1 実機は未検証。

## 2026-11-25 読み取り専用ロックと削除待ちの修正

更新ヘルパーは存在する旧ロックを読み取りアクセスで開き、不足時だけ新規作成する。
整理できない旧ロックは対象名と理由を報告して保持する。旧ロックに競合がなければ、完了済みの
バックアップを退避する。

削除待ちも Win32 ではアクセス拒否になるため、アクセス拒否時だけネイティブの状態を確認する。
削除待ちまたは既に消えたことを確認できた場合は競合として扱い、旧作業フォルダが削除待ちでも
更新準備と起動を継続する。
バックアップ移動では Windows の拡張長パスを使い、同名の退避先を上書きしない。

- Windows 11 で `bmz-updater` の43テストが成功した。読み取り専用の旧ロックによる排他取得、
  ACL による削除拒否を再試行せず報告すること、260文字超の退避パス、同時退避、削除待ちの
  作業フォルダがある状態での起動と更新準備を確認した。
- `cargo fmt --check`、workspace の `check` と全ターゲットの Clippy、
  `cargo test --workspace --locked --no-fail-fast -j 1` が成功した。
- `x86_64-win7-windows-msvc` の検証用 v0.5.5 を、公式 v0.5.4 ポータブル版のヘルパーで適用し、
  自動再起動での退避と旧ロックの削除を確認した。
- 別の隔離コピーでは旧ロック2本を読み取り専用に設定し、修正済みヘルパーで同じ更新を適用した。
  自動再起動後に両ロックの属性、退避したバックアップとログ、ユーザーデータが保持された。
  公開フィード経由、SMB 共有、Windows 8.1 実機は未検証。

## 2026-11-25 再レビュー対応

`9fedde9d2` の再レビューで見つかった7件を修正した。

- 新配置の `updater/instance.lock` と `updater/update.lock` も、既存のファイルは読み取りアクセスで開く。
  不足時だけ作成するため、読み取り専用属性が付いたロックでも起動と更新ヘルパーが動く。
- 旧ロックの位置にあるディレクトリや reparse point はロックとして使わない。
  整理では残して報告し、起動と更新準備は止めない。
- 更新の適用で使う rename にも Windows の拡張長パスを使い、260文字を超える配置先でも適用できるようにした。
- 残した旧ロックは、バックアップの退避や旧ロックの削除を行った起動でまとめて報告する。
  整理する対象がない起動では報告を繰り返さない。
- 新配置の更新ヘルパーは、旧配置の本体メタデータか旧作業フォルダの未完了記録がある場合だけ旧ロックを作成する。
  残した `.bmz-instance.lock` があっても、削除済みの `.bmz-updater.lock` を作り直さない。
- ロック作成時のアクセス拒否は、削除待ちの場合だけ再試行の対象にする。
  作成権限がない場合は、500msの再試行をせずに報告する。
- v0.5.4 以前の更新ヘルパーはロックを書き込みアクセスで開くことを [自動更新](../../docs/auto-update.md#windows-portable) に記載した。

## 2026-11-25 長い作業パスでの SxS 起動確認

長い作業パスで ZIP を展開・適用した後も、SxS 版は `startup-probe` をカレントディレクトリに使うため、
Windows 11 で起動確認が OS エラー267となり、旧版に戻ることがあった。
起動確認には空の一時ディレクトリを作り、更新作業フォルダに作ると長すぎる場合は Windows の一時フォルダを使う。
確認用ディレクトリは確認処理を抜ける際に破棄し、`startup-version.txt` は更新作業フォルダに残す。
Windows の一時フォルダにも短い確認用ディレクトリを作れない場合は、理由を報告して旧版に戻す。

- 260文字を超える作業パスで、短い隔離先から子プロセスを起動でき、終了後に一時ディレクトリを破棄できる回帰テストを追加した。

  自動再起動したメインウィンドウの表示、旧実行ファイルのバックアップとユーザーデータの保持を確認した。
- 配置先242文字、作業パス284 UTF-16コード単位でも SxS の起動確認と適用は成功した。

## 2026-11-25 更新適用と再起動の結果分離

配置先を Windows の作業ディレクトリとして使えない長さの場合は、再起動時にヘルパーの作業ディレクトリを継承する。
更新の適用が成功し、再起動のプロセスを開始できない場合は、更新済みとして手動起動を案内する。
再起動に失敗した理由も `update.log` に記録する。適用や復旧自体が失敗した場合は、その失敗を報告する。

- SxS の起動確認用ディレクトリは標準ライブラリのみで作成・削除する。Windows 互換ターゲットの通常依存関係から
  `tempfile` と `getrandom 0.4` が外れたことを確認した。
- 起動確認の一時フォルダも長すぎる場合のエラー、`startup-version.txt` の出力先と確認用ディレクトリの削除、
  検証用の実行ファイルで深い配置先からの起動、適用済みの状態で再起動に失敗した場合の警告をテストした。
- Windows 11 の配置先293・作業パス331 UTF-16コード単位で、修正済み Windows 互換ヘルパーを使い、
  SxS フィクスチャの更新、起動確認の出力・一時ディレクトリの削除、短い作業ディレクトリを継承した再起動を確認した。
- 別の通常の長さの配置先では、公式 v0.5.4 の隔離コピーに修正済みヘルパーで検証用 v0.5.5 を適用した。
  自動再起動、読み取り専用の旧ロック2本の属性保持、バックアップとログの退避を確認した。
- `cargo fmt --check`、workspace の `check`、全ターゲットの Clippy と workspace 全テストが成功した。

- 配置先242文字、作業パス284 UTF-16コード単位の Windows 11 で更新を適用し、
  起動した本体が winit 0.30.13 の `RegisterDragDrop` で `0x8001FFFF` を返して異常終了した。

  安全に続行できない場合は、失敗した API とパスが分かる起動エラーを表示する。
