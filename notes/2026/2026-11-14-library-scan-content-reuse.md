# 同一譜面の解析再利用と大規模スキャンの待ち時間

2026-11-14、Windowsの実ライブラリを使い、[前回の高速化](2026-11-14-library-scan-followups.md)の
`a104f333` を基準に案1、3、2の順で比較した。
ビルドは `cargo build -p bmz-player --release --locked --offline --no-default-features --bin bmz-player`。
スキャンは `--no-everything` を指定し、設定・ライブラリDB・キャッシュは計測用のコピーに分けた。

## 案1　bms-rsのオブジェクトID変換

`bms-rs 1.0.0` の作業用コピーで、ASCIIのオブジェクト列を2文字ずつ借用し、`00` を変換前に飛ばした。
16進値も元の文字列から借用し、非ASCIIの入力には既存処理を使った。

- EVENTSからBMS系700譜面を選び、前後を交互に各2回計測した。トークン処理は
  **3.49〜3.54 → 1.47〜2.02 ms/譜面**、取り込み全体は **9.2〜9.8 → 6.0〜8.2 ms/譜面**。
- EVENTSの3,126件を全件再解析した前後各3回の中央値は **3,373 → 3,256 ms**。
  計測範囲は基準3,347〜3,605 ms、試作3,199〜3,460 ms。パスごとのDB出力は一致した。
- 3,025譜面を4通りの乱数指定で解析したダイジェストも一致した。

トークン処理単体では短縮した。スキャン全体では中央値で3.5%の差に留まるため、試作を
`.local/scan-perf-20261114/bms-rs-object-ids.patch` に保存し、製品側の依存指定は維持した。

## 案3　ネイティブ探索中に素材のフルパスを作らない

列挙結果のファイル名と種別から対象を絞り、譜面・書庫・フォルダ・リンク・エラーの記録にパスが必要な
場合に組み立てる。譜面拡張子はASCIIで大文字小文字を区別せず照合する。

INSANEの69,431件を変更なしで差分更新し、前後を交互に各5回計測した。中央値で探索は
**572 → 497 ms**、全体は **942 → 856 ms**。DBに保存したパスごとの出力は一致した。

## 案2　同一内容・同一形式の解析結果を共有

同じサイズの候補が複数ある場合に、読み取ったバイト列のSHA-256と解析形式で照合する。通常ファイルと
書庫の両方が、解析済みの保存用データと警告を同一スキャン内で共有する。譜面のイベント列はキャッシュに
保持しない。上限は65,536キーと保持データ192 MiB。登録パス、更新日時、プレビュー解決はファイルごとに
扱う。異なる解析形式と失敗結果は共有しない。既存のDB形式と取り込みバージョンを維持した。

10ルート・126,874件を列挙し、旧バージョンのDBから1件を除く全譜面を再解析した初回比較。

| 指標 | 案3まで | 案2適用 |
| --- | ---: | ---: |
| 全体 | 690.0秒 | 508.6秒 |
| 通常ファイルの書き込み | 104.1秒 | 94.2秒 |
| うちコミット | 57.8秒 | 48.2秒 |
| 解析結果の再利用 | 0件 | 10,061件 |

初回の2実行は一部が重なった。約600万ノーツの1譜面の処理時間やディスク条件も全体に影響するため、
この26.3%差には解析再利用以外の影響が含まれる。
両方で成功126,766件、失敗107件、警告217,796件。今回の対象外の登録も含め、DBの127,805パスを比較した。
ファイル情報・ハッシュ、譜面情報、統計、警告の内容と順序が一致した。行IDと実行時刻は比較から除いた。

最後に残った `bug.bms` 1件だけを再解析済みとした別のDBコピーを使い、同じ10ルートを順に計測した。
全体は **222.6 → 124.4秒**、再利用は **10,079件**。変更なしの再スキャンは **1,907 → 1,811 ms** で、
両方とも126,874件をスキップした。全パスのDB出力は一致した。大規模計測は各条件1回で実行順とディスクの
状態による変動を含む。

EVENTSから700譜面を選び、同じバイト列を4ルートに配置した。再解析を前後で交互に各5回実行した
中央値は **3,507 → 1,015 ms**。再利用は2,097件で、同梱の1件を含めたDB出力も一致した。

## 案4　大規模スキャンのバッチ待ち

通常ファイルについて、バッチごとに解析結果を受け取るまでの時間、SQLite書き込み、コミットを計測する。
500 ms以上かかった譜面はワーカー側で、ファイル読み込み、取り込み、統計、保存形式への変換に分けて記録する。
書き込みと解析は並行し、ワーカー経過時間の合計は全体時間と直接比較できない。

案2適用版の10ルート計測で、最後の44件は結果待ち **351.8秒**、書き込み **245 ms**、うちコミット
**5 ms**。他の496バッチの最大待ちは **1.75秒**、最大書き込み **492 ms**、最大コミット **306 ms**。
案3までの版でも最後の2バッチのログ間隔が **467.5秒** あり、最後のバッチの書き込みは **252 ms** だった。
前回の74秒の書き込みは今回再現しなかった。

案2適用版では、13.4 MBの `bug.bms`（ラプラス）1件の取り込みに **47.6秒**、統計に **374.0秒**かかった。
同じ譜面の単独計測では、読み込み・デコードから中間表現まで **3.44秒**、正規化 **25.19秒**。
正規化後は5,844,982ノーツ、7,460のLNペアで、各LNの始点をレーン内で線形探索してダミー判定する
1周だけで **26.26秒** だった。正規化にもLN始点の線形探索があり、ライブラリ統計ではLN集計、LN種別、
密度分布が同じ始点の探索を繰り返す。次は始点の照合をまとめ、統計の各処理で同じ探索を繰り返さない形を検討する。

`bug.bms` を再解析済みとした計測でも、最後の43件では **30.6秒**待った。別の譜面の取り込みと統計に
それぞれ **22.3秒**、**28.6秒**かかり、そのバッチの書き込みは **38 ms**、うちコミットは **3 ms**だった。
