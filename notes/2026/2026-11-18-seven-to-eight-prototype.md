# 7K→8K変換の試作

7Kの鍵盤7レーンを8レーンへ広げ、スクラッチを空いた鍵盤レーンへ移す変換
`KeyModeConversionConfig::SevenToEight`（表示名`7K TO 8K`）を試作しました。
実機で試して評価するための試験的な実装で、値と規則は調整を前提にしています。
既存の7K→6K変換（`seven_to_six.rs`）に倣い、実装は
`crates/bmz-player/src/screens/play_session/seven_to_eight.rs`です。

## 統合

- 対象はKeyMode::K7の譜面だけです。変換後の譜面は`KeyMode::K8`（Key1..Key8、スクラッチなし）です。
- 譜面オプションは7K→6Kと同じく`RANDOM-EX`→`RANDOM`、`S-RANDOM-EX`→`S-RANDOM`、
  `ALL-SCR`→`NORMAL`へ正規化し、2P側の配置は`NORMAL`にします。
  配置seedが無いときは7K→6Kと同じ経路で生成します。
- ジャック判定の閾値はH-RANDOMの閾値（記録が無ければ既定125ms）です。
- `SpToDp`・`SevenToSix`と同じく`score_save_disabled`です。
  replay再生時もこの変換は無効化されます（[スコア保存](../../docs/score-persistence.md#key-mode-変換)）。

## ブロック

`NoteEvent`は小節番号を持ちませんが、`PlayableChart::bar_lines`が小節番号・tick・時刻を持ちます。
ノートはtickが同じか手前にある最後の小節線の小節に属するものとし、最初の小節線より前は1つのブロックにします。
先頭余白で小節線もtickごと移動するため、余白の有無で分け方は変わりません。

異なるtickの小節線が2本未満の譜面（`lines`が空のBMSONなど。先頭余白で原点の1本だけが入る）は、
最初のノートの時刻から2000msの固定窓（`FALLBACK_BLOCK_US`）で分けます。

## 空きレーン（gap）

ブロックごとにgap g（1..8）を選び、鍵x（1..7）を`x < g`ならx、それ以外はx+1へ置きます。

### 依頼の式からの変更

依頼の`score(g) = Σ count_l^2 + λ・total・[g != prev_g]`は、レーン単位の`Σ count_l^2`が
gに依存しません。埋め込みは7本のレーンを丸ごと別の位置へ移すだけで、レーンごとの個数の組は変わらないためです。
この式のままでは切替コストだけが残り、最初のブロックのgapから変わりません。

最初の試作では負荷項を左右の手の個数の二乗和（`L(g)^2 + R(g)^2`、L = レーン1..4、R = レーン5..8）にしましたが、
試奏の結果を受けて、レーン位置で重み付けした二乗和に差し替えました（`gap_load_score`）。

さらに2回目の試奏の結果を受けて、同時押しの隣接ペア項（`simultaneous_adjacency`）を加えました。

```text
score(g) = Σ_{l=1..8} W[l]・count_l(g)^2 + μ・sim(g) + λ・total・[g != prev_g]
count_l(g) = gap gで埋め込んだ後にレーンlへ入る鍵盤ノーツ数（gapレーンは0）
W = [2.0, 1.4, 1.1, 1.0, 1.0, 1.1, 1.4, 2.0]（LANE_LOAD_WEIGHTS）
sim(g) = Σ_{同時刻グループ} gap gで埋め込んだ後の、同じ手の中で隣り合うレーンのペア数
μ = 16.0（SIMULTANEOUS_ADJACENCY_WEIGHT）
```

レーン1..4を左手の小指・薬指・中指・人差し指、レーン5..8を右手の人差し指・中指・薬指・小指とみなし、
弱い指ほど重みを大きくしています（小指2.0、薬指1.4、中指1.1、人差し指1.0）。
重みはレーンごとに異なるため、レーン単位の二乗和でもgごとに差が出ます。
重みは調整用の値です。実装では10倍の整数で持ち、左右対称のgap（1と8など）が浮動小数の誤差なく同点になるようにしています。

想定する挙動は次のとおりです。

- KEY1が多いブロックではgap 1が選ばれやすく、レーン1が空いてKEY1はレーン2（薬指）へ移ります。右側も対称です。
- 単音中心の均一なブロックでは重みの最も大きい端を空ける方が安く、gapは1または8に寄ります。
  1と8が同点のときは既存のtie-break（前のgapに近い方、最初のブロックは中央に近い方、さらに小さい方）で決まります。
- λ = 1.0のままでは、ノーツの少ないブロックでは負荷差が切替コストを下回り、gapは切り替わりにくくなります。
  例として片側4鍵に各n個ずつ偏ったブロックでは、端へ移す利得はn²、切替コストは4nなので、n > 4で切り替わります。

#### 差し替えの根拠

試奏で「KEY1とKEY8にノーツが偏り、特にKEY1で小指の負担が大きい」との報告がありました。
旧コスト（左右の手の二乗和）で合成譜面を変換したレーン別鍵盤ノーツ数は次のとおりで、
gapがほぼレーン4 / 5に張り付き、端のレーンが元の端の鍵をそのまま受け持っていました。

| 譜面 | 変換後レーン1..8の個数 |
|---|---|
| 均一（元は全鍵80個） | [80, 80, 80, 0, 80, 80, 80, 80]（全小節gap 4、レーン4が常に空き） |
| 両端多め（元KEY1 / KEY7が120個） | [120, 88, 80, 0, 96, 80, 88, 120]（レーン1・8が最多、レーン4は0） |
| 左右交互に偏る | gapが4 / 5を往復し、レーン4・5がKEY4を半分ずつ（各24個）、レーン1・8がKEY1・KEY7を全数（各100個） |

新コストでの同じ譜面の再計測は未実施です。

### 同時押しの隣接ペア項

同時刻に隣り合うレーンを同じ手で押すのが最も負担が大きいとみなし、その組の数をコストに加えます。

- ブロック内の鍵盤のTap・LongStart（地雷は除く）を、開始時刻（`TimeUs`）の完全一致でグループに分けます。
  スクラッチの同時刻グループと同じ流儀です。同じ鍵の重複は1つにまとめ、1鍵だけのグループは数えません。
- 各グループの到達レーン集合のうち、左手（レーン1-4）または右手（レーン5-8）の中で隣り合う組を数えます。
  レーン4と5は両手にまたがるので数えません。
- 密集した和音の内側にgapが入ると隣接ペアが減るため、和音の多い区間では中央寄りのgapが勝てます。
  単音だけの区間ではこの項は0で、負荷項と切替ペナルティだけの従来の挙動のままです。
- 例: 左手の和音KEY1..KEY4をn回押す小節では、gap 1が4.5n² + 32n、gap 2が5.1n² + 16n、
  gap 3が5.4n² + 16n、gap 4が5.5n² + 32n、gap 5..8が5.5n² + 48nです。
  n < 26.7でgap 2がgap 1より安くなります（n = 8で454.4対544.0）。
- 7鍵すべての和音では、gap 1・4・5・8で5組、gap 2・3・6・7で4組です。
  和音1つの小節ではgap 2と7が73.6で同点になり、tie-breakで2を選びます（gap 1・8は89.0）。

#### 追加の根拠

重み付き負荷項に差し替えた後の試奏で、「大部分が端への単純シフト変換になっていた」との報告がありました。
現実的な分布の譜面で計測すると、gapは端（1か8）にしかならず、中央のgapは一度も選ばれませんでした。
「小指のレーンを空ける」ことが支配的で、典型的な小節では中央のgapが端のgapに約135〜190点負け、
切替ペナルティ（約77点）を上回るためです。単音中心の区間の挙動は変えずに、和音の区間で中央寄りのgapが
選ばれる余地を作るため、同時押しを直接見る項を加えました。

### 規則

- countは鍵盤のTap・LongStart・Mineの個数です（LNは始点だけを数えます）。
  LongEnd・不可視ノーツ・スクラッチは数えません。totalは同じ個数の合計です。
  同時押しの隣接ペア項は、このうちTap・LongStartだけを使います。
- λ = `GAP_SWITCH_PENALTY_PER_NOTE` = 1.0、μ = `SIMULTANEOUS_ADJACENCY_WEIGHT` = 16.0です。
- 前のブロックから続くLN（鍵盤・スクラッチ）があるブロックは、前のgapに固定します。
  LNの終点が次の小節線と同じtickにある場合も、終点側のブロックを固定します。
- 鍵盤ノーツの無いブロックは前のgapを維持します。最初に鍵盤ノーツがあるブロックより前は、そのブロックのgapを使います。
- 同点は前のgapに近い方、さらに同点なら小さい方を選びます。最初のブロックは中央4.5に近い方、
  さらに同点なら小さい方です。gapの選択に乱数は使いません。
- LNは始点側のブロックのgapで両端を付け替えます。

## スクラッチ

7K→6Kの可動ユニット（単ノーツとLNの組）、同時刻グループ、BGM化、`can_place`を共有します。
`seven_to_six.rs`の`MovableUnit`・`can_place`・`jack_relevant`・`push_note_sounds_as_bgm`を`pub(super)`にしました。

- 候補は変換後の鍵盤ノーツと配置済みのスクラッチに対して、時間範囲が重ならず、
  H-RANDOM閾値以内に押すノーツが無いレーン（Key1..Key8）です。LNは区間全体と両端を見ます。
- 優先順は、直前に配置したスクラッチのレーン、ユニットの始点ブロックのgap、
  直前のスクラッチレーンに近い順（同距離はgapに近い方、さらに小さい方）です。
  直前のスクラッチが無い場合は、gap、gapに近い順、小さい順です。
- 各ユニットで候補レーンをこの順に並べた順位をコストにし、同時刻グループでは配置数が最大、
  次に順位の合計が最小の割当から、7K→6Kと同じseed付きRNGで選びます（RNG domainは別の値です）。
  グループ内で複数を配置したときは、並び順で最後のユニットのレーンを「直前」にします。
- 置けないユニットはBGMにし、不可視のスクラッチは捨てます。

### 依頼のテスト条件からの変更

「同時刻に7鍵すべて＋スクラッチがある場合はBGM化」は、gapレーンがその時刻に空いているため成立しません。
テストでは、直前のスクラッチがgapレーンのジャック閾値内にある場合にBGM化することを確認しています。

## テスト

`seven_to_eight.rs`のモジュール内テストです。

- 左寄りの小節の次に右寄りの小節があると、重い側の端が空き、gapが1→8へ切り替わる（小節線あり・固定窓）
- KEY1が突出して多い小節ではgapが1になり、レーン1に鍵盤ノーツが無く、KEY1がレーン2へ移る（直前の小節はgap 8）
- 左手の和音KEY1..KEY4を8回押す小節ではgapが2になる（端ではなく和音の内側が空く）
- LNが小節を跨ぐとgapを切り替えない
- スクラッチがgapへ移り、閾値内でgapが塞がると7鍵の和音と同時のスクラッチがBGMになる
  （7鍵の和音ではgap 2と7が同点で、小さい方の2を使う。隣接ペア項の追加前はgap 1と8の同点で1）
- 左寄り・右寄りの小節とKEY1が突出する小節のテストは、同時刻になるノーツの組（例: KEY1とKEY3）が
  元から隣り合わず、埋め込みでも隣り合わないため、隣接ペア項は0で期待値は変わらない
- スクラッチLNの始点・終点が同じレーンになる
- 変換後がK8で、鍵盤ノーツ数（不可視・地雷を含む）が保たれる

実機での評価と、cargoによるビルド・テストは記録時点で未実施です。

## 未確認・残課題

- 重み付き負荷項と同時押しの隣接ペア項が試奏で意図に合うか。W・μ・λの釣り合いと、
  現実的な譜面で中央寄りのgapが選ばれる割合の再計測が必要です。
- 均一な譜面では端のレーンが空き続けるため、端の指を使わない配置が続くことへの評価が必要です。
- スキンのoption（7K→6Kの`19189`相当）は追加していません。
- 設定説明の翻訳文（`settings-entry-description-key-mode-conversion`の「DP、9K、6K」）は更新していません。

## 2026-11-19　4小節単位の打鍵履歴

小節内の鍵盤数だけで評価すると、同じレーンが曲の大半で空くことがありました。
元の4小節を1区間とし、区間の先頭で過去の出力レーン別打鍵数 `H` を0.75倍にします。
候補の出力レーン別打鍵数を `c` としたとき、鍵盤の負荷項は
`2 × Σ(H[l] × c[l]) / Σc[l]` です。これは履歴と今回の打鍵数を足した二乗和から
配置によらない項を取り除き、今回の総打鍵数で割った値です。
同手の隣接同時押し1組に0.15、空きレーン1本分の移動に0.25を加えます。
採用した配置の通常ノーツとLN始点を履歴に加え、休符だけの区間でも履歴を減衰させます。
境界での縦連、トリル・階段、LNの扱いは[配置の仕様](../../docs/score-persistence.md#7k8kの配置)に記載しました。

Windowsで「運命論」の4譜面を同じimport経路に通し、変更前後のRust変換関数を直接比較しました。
条件はseed 1、H-RANDOM閾値125ms、変換後の追加配置なしです。
数値はスクラッチ移動後の全打鍵に占める、最少レーンと最多レーンの比率です。

| 譜面 | 変更前 | 変更後 | 変換後の打鍵数（前後共通） |
|---|---:|---:|---:|
| NORMAL | 7.2〜16.6% | 10.7〜17.6% | 403 |
| HYPER | 2.9〜15.9% | 9.7〜14.5% | 1,576 |
| ANOTHER | 4.7〜15.3% | 10.2〜13.5% | 2,628 |
| MODERATE | 2.7〜15.5% | 9.0〜13.7% | 1,360 |

HYPERのKEY8は45打から153打に増えました。NORMALは最少レーンの打鍵率が上がり、
最多のKEY5は17.6%になりました。ANOTHERでは変更前後ともスクラッチ1打がBGMになりました。
Windowsでfmt、対象crateのcheck、全ターゲットのClippy、Releaseビルドが通りました。
`cargo test -p bmz-player --locked --no-fail-fast -- --test-threads=1` は3,343件成功、
失敗0件でした（ライブラリ94件、Windows起動テスト2件はignored）。
実機での試奏と、別の曲での分布は未確認です。

## 2026-11-20　フレーズ単位の変換

4小節間で同じ7本を使うと、鍵盤だけでは1小節内で8本すべてを使えませんでした。
変換を[フレーズ単位の配置](../../docs/score-persistence.md#7k8kの配置)に変更しました。
同じ時刻の鍵をまとめて扱い、縦連・交互打ち・階段を作る打点をつなぎます。
例えば階段の最後の鍵から縦連が始まる場合は、共有する打点も含めてまとめます。
4小節の区切りは打鍵履歴の減衰に使います。

「運命論」の4譜面をWindowsで変更前後のRust変換関数に通し、1小節で8本すべてを
使った小節数を比較しました。seed 1、閾値125ms、変換後の配置はNORMALです。
各譜面で打鍵を含む小節は115。元のノートIDを使って鍵盤由来の打鍵と皿を区別しました。

| 譜面 | 鍵盤由来の打鍵が8個以上ある小節 | 鍵盤だけで8本（旧→新） | 皿を含めて8本（旧→新） |
|---|---:|---:|---:|
| NORMAL | 17 | 0→1 | 0→1 |
| HYPER | 68 | 0→35 | 4→36 |
| ANOTHER | 101 | 0→67 | 6→70 |
| MODERATE | 67 | 0→37 | 3→38 |

変換後の総打鍵数は変更前と同じでした。ANOTHERは変更前後とも皿1打がBGMに移り、
ほかの3譜面は全打鍵を保持しました。Windowsでfmt、対象crateのcheck、
全ターゲットのClippy、Releaseビルドを確認しました。プレイヤーのテストは
3,393件成功・失敗0件で、変換の回帰テスト9件を含みます。実機での試奏は未実施です。
