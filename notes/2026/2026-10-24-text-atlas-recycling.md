# 文字atlas満杯時のスパイクの調査・行の再利用

## 対象と条件

- 基準: main `a92ab8bb`（PR #45マージ後）。修正: `b1fba847`（診断）、
  `a434cae2`（行回収）、`78f04da5`（回帰5件）、`9ce982e9`（全消去後だけ再試行を遅らせる）。
- 実施日: 2026-10-24、Windows、i9-12900K、RTX 5090、driver 32.0.16.2101。
  Rust/Cargo 1.98.1。DX12 / Vulkan、4Kボーダーレス、1440pウィンドウ、DX12 144Hz VSync。
  VSyncは`\\.\DISPLAY1 [-3840, 0]`を明示し、約6.94msの間隔を確認した。
  primaryの240Hzで採った最初のVSync試行は比較から除外する。
- LIGHT1440、TTF、Shrink、縁取り0.7。日本語タイトルを含む19,589件のINSANEフォルダ。
  起動・フォルダ移動後に5秒待ち、50msごとに400回移動する20秒間を記録する。
- 個人のconfig/DBとは独立した`.local/atlas-spike/runtime`を使用する。
  元の計測用DBはSQLite backupで複製し、OBS・IR・更新・自動scanを無効にした。
- 同じローカル限定ドライバを両ビルドへ加え、releaseで測定した。driver、CSV、生ログ、
  スクリーンショット、B案の試作差分は`.local/atlas-spike/`に保存し、コミットしない。
  計測中はCargoを動かさず、ウィンドウを1つずつ実行した。

`interval_us`はrender終了点同士の間隔、FPSはその逆数から求めたアプリの進行頻度であり、
実際の表示周期ではない。PresentMonは使っていない。
`work_us`はscene snapshot・video更新・plan・renderの壁時計時間（surface待ちを含む）。
入力・egui等を含む全redraw時間とは区別する。以下の分位は各CSVの全sampleをソートした値。
個別時計と全グリフ集計を有効にした診断実行は、性能比較と分ける。

## 原因の切り分け

対策前に、指定mainに診断だけを加えて測定した。

| 診断・20秒 | 4K DX12 | 1440p DX12 |
|---|---:|---:|
| 全消去 | 16回 | 5回 |
| 消去間隔の平均（イベント間） | 1.199秒 | 2.873秒 |
| 満杯直前の格納グリフ | 521～878 | 975～1,227 |
| font内glyph IDの組（font別） | 259～395 | 439～636 |
| 縦横倍率の組 | 12～34 | 20～35 |
| 過去3フレームの画素 / atlas容量（padding込み、平均） | 23.06% | 10.58% |
| 再ラスタライズ数 / 消去frame（平均） | 279.44 | 272.60 |
| 再ラスタライズCPU時間（平均） | 4.197ms | 2.134ms |
| その他の文字準備（平均） | 2.032ms | 1.564ms |
| 消去frameの転送量（平均 / 最大） | 6.928 / 8.940MiB | 3.047 / 4.233MiB |
| 容量不足の未描画要求があったframe | 16 | 5 |
| 未描画要求数（装飾重複込み） | 1,737 | 225 |
| 消去したframeの未描画要求 | 0 | 0 |

参照窓は「最後に使ってからの経過が3フレーム以下」。基準の診断は次frameの組立前なので
過去3frame、修正版の行回収は組立中なので現在と過去3frameになる。
4Kでは4 font、全てvectorグリフだった。縁取りと影は元のvector画素を共有している。
font・glyph ID・縦横倍率・種類の詳細は満杯時のtraceで取得できる。
`characters`はUnicode文字数ではなく、font内glyph IDの組（合字等を含む）。
未描画要求は影・縁取りの重複を含み、実際の文字数としては数えていない。

4Kの消去frameのatlas転送は平均2.023ms。ラスタライズに加えてレイアウト等の再構築と
多数の部分転送が同時に発生していた。`layout_and_pack_us`は差分値であり、
純粋なlayout時間ではない。診断出力とインスタンス符号化等も含む。
1画面が常に容量を超えるのではなく、画面外へ出た文字の倍率違いが蓄積していた。

## 候補の比較

| 案 | 判断 |
|---|---|
| A: 古い行の回収 | 採用。現役の画素・座標・GPUテクスチャを維持でき、保持グリフのコピーと再転送が不要 |
| B: 現役グリフの詰め直し | 試作して測定後に不採用。ラスタライズは減るが、CPUコピー・layout座標更新・再転送が重い |
| C: 複数ページ | 未実装。instance/UV、bind、shader、ページ寿命の変更が必要で、今回の修正範囲が大きくなる |
| D: 幅2048 | 未実装。上限8192のRGBA8ならGPU atlasは32→64MiB、追加32MiB。CPU画素容量や初期全転送も増え、全消去の仕事自体は残る |
| E: 複数frameへ分割 | 未実装。旧配置を表示しながら新配置を公開する管理が必要。今回の行回収より変更が大きい |

B案は同じ4K DX12条件で復旧frameの処理が平均9.610→12.584msと悪化した。
別の診断では、再ラスタライズ数は平均279.44→26.56へ減ったが、コピー対象が平均7.75MiB、
詰め直し自体が平均3.925msだった。ラスタライズ以外の文字準備も平均7.750msへ増えた。
一時的な画素buffer容量（コピー元・コピー先・dirty画素の和）は最大約77.5MiBになった。
この試作は最終差分に含めない。

## 実装と互換性

- 現在と過去3フレームでglyph hitまたはlayout hitがあった行を保護し、古い行を空ける。
  同じ行にある古いグリフも残すので、個々のグリフのLRUより保守的な回収になる。
- 行ごとの高さと使用済み横幅を保持し、低い行から新しいグリフを格納する。
  現役グリフの座標・画素を動かさない。
- 追い出した行を参照するlayoutは全体を無効にする。`capacity_misses`による
  欠けたlayoutのキャッシュ抑止は維持する。layout上限で参照情報が消える場合も参照時刻を引き継ぐ。
- 再利用領域の透明な1px paddingをCPU/GPUとも上書きする。救済前に追加したdirty regionも
  引き継ぎ、GPUへ渡す前にそのframeを組み直す。
- 救済不能なら空のatlasでも試し、従来の全消去・再試行待ちへ戻す。
  60frameの待機は全消去後だけに限定する。行回収だけでは空atlasを試したことにならない。
- PR #45の倍々の確保、縮めないGPUテクスチャ、部分転送、位置非依存layout、装飾の共有、
  Shrinkの1オクターブ16段階、非有限座標の除外を維持する。SDFや縁取り焼き込みは追加しない。

GPU atlasの上限は1024×8192 RGBA8の32MiBで変わらない。CPU側には参照時刻、行の表、
回収時の一時集合を追加する。全画素をコピーする追加bufferは不要。プロセス全体のRSSは未計測。

## 最終コードのWindows実機比較

修正版は`9ce982e9`、CSV名の`final-*`。基準は`main-*`で、VSyncは追加の連続ペア
`main-Dx12-2160-True-4-144hz`と`final-Dx12-2160-True-4-144hz`を使う。
単位はms。矢印はmain→修正版。各20秒、詳細診断を無効にした実行である。

「復旧」は全消去に加え、修正版では行回収も含む。回収の回数自体は増える。

| 条件 | 復旧回数 | 復旧frame平均 / 最大 | 通常frame平均text | アプリFPS |
|---|---:|---:|---:|---:|
| 4K DX12 | 16→41 | 9.610→4.185 / 12.320→13.351 | 0.198→0.195 | 1193.47→1178.71 |
| 4K Vulkan | 16→36 | 8.502→4.078 / 10.560→11.549 | 0.195→0.191 | 1291.87→1307.54 |
| 1440p DX12 | 5→11 | 5.997→2.793 / 7.129→7.401 | 0.197→0.193 | 1174.34→1206.40 |
| 4K DX12 144Hz VSync | 17→37 | 10.051→7.829 / 12.677→15.025 | 0.436→0.356 | 143.96→143.97 |

4K DX12の追加ペアはmain 1119.93FPS / 通常text 0.203msに対し、採用実装の再試行待ち修正前は
1232.79FPS / 0.189msだった。初回VSyncはmain 0.356ms、修正前の採用実装0.372msであり、
0.016msの増加もあった。短時間のFPSや小さな時間差には実行間のばらつきがある。
通常textの大きな悪化は観測しなかったが、全環境で悪化ゼロを統計的に保証したものではない。

### 文字準備・転送

| 条件 | text最大 | atlas転送CPU最大 | 復旧frameのatlas転送CPU平均 |
|---|---:|---:|---:|
| 4K DX12 | 8.179→9.303 | 10.740→11.035 | 1.842→0.444 |
| 4K Vulkan | 7.296→9.030 | 12.749→12.070 | 1.154→0.359 |
| 1440p DX12 | 4.262→4.945 | 10.857→10.814 | 1.664→0.259 |
| 4K DX12 144Hz VSync | 8.633→10.412 | 11.504→11.236 | 1.806→0.546 |

DX12で転送CPU最大11.035msのsampleは、復旧0、write 1、転送32MiBだった。
GPUテクスチャが8192pxへ伸びる全転送であり、行回収の転送とは分ける。
4K DX12の復旧frameの平均転送量は7.104→2.111MiBだった。
復旧の平均間隔は4K DX12 0.450秒、Vulkan 0.496秒、1440p 1.259秒、VSync 0.482秒。
軽い行回収が増えたので、「復旧間隔が長くなった」という改善ではない。

別実行の最終診断（`final-Dx12-2160-False-2`、20秒）では、行回収37回、全消去8回。
対策前の全消去16回から半減した。行回収CPUは平均0.162ms / 最大0.413ms。
現在と過去3frameが参照する行は全体の平均88.29%で、同じ回収frameの画素23.70%より広かった。
これが全消去をゼロにできなかった理由である。
未描画要求があったframeは16→4、要求数は1,737→63へ減少し、復旧frameでは0だった。
復旧frameのラスタライズは平均76.78グリフ / 1.712ms、その他の文字準備は平均1.511ms。
CPU画素bufferの確保容量最大は49,807,360bytes（47.5MiB）。GPU atlasは両ビルドとも
1024×8192、32MiBで、回収・全消去ではGPUテクスチャを再作成していない。

## 自動検証

既存テストを変更せず、`text_atlas_upload.rs`へ5件を追加した。

1. 320frameの文字列・倍率の入替で、従来動作より全消去が減り、欠けが増えない。
2. 縁取り・影、Shrink、color/silhouette、bitmap、styled fallbackを混ぜ、
   全格納グリフとpaddingを模擬GPUで検証し、各quadの参照画素をfresh atlasとも比較する。
3. layout上限でキャッシュが消えても、最近使ったglyphの参照が失われない。
4. 追い出した行を参照するlayoutを再利用せず、96px上限でも正しい画素で組み直す。
   行に収まらない大きな1文字を誤って60frame待たせないことも確認する。
5. 1frame分が96px atlasに収まらない場合、毎frame全消去しない。

fixture fontは全て存在し、混在試験はvector / bitmap / color / silhouette / styled fallbackが
実際に使われたことをassertしている。外部素材がない場合の早期returnで成功扱いにしていない。

- `cargo fmt --all -- --check`: 成功。
- `cargo test -p bmz-render --lib --locked`: 944 passed、0 failed、10 ignored。
- `cargo check -p bmz-render --locked`: 成功。
- `cargo clippy -p bmz-render -p bmz-player --all-targets --locked -- -D warnings`:
  既存`text_non_finite.rs:52,53`の`chunks_exact_to_as_chunks` 2件で失敗。
  mainのソースそのものに戻した実行でも同じ2件を再現した。既存テストの書換えやlint抑制はしない。
- 追加確認の`--lib --bins --examples` Clippy: 成功。
- 基準mainの`cargo test -p bmz-player --locked`: 2648 passed、0 failed、39 ignored。
  別枠のネイティブ起動テスト2件も既存ignore。今回のWindowsでは申告された約25件の失敗は再現しなかった。
- 最終ソース（計測driver除外）の`cargo test -p bmz-player --locked`も
  2648 passed、0 failed、39 ignored、起動テスト2件ignoreで基準と同じだった。
- `cargo build -p bmz-player --release --locked`: 各比較用ビルドで成功。
  最終計測は`9ce982e9`に同じローカルdriverだけを追加したもの。

## 表示の確認と未検証事項

mainと修正版の3840×2160スクリーンショットを目視比較した。取得した静止画に欠け、にじみ、
古い画素の残りは見えない。時計・FPSを除いた左側のタイトル・メタデータ領域
`(80,700)-(2100,1300)`は画素差0だった。動く光や時計がある画面全体の完全一致は主張しない。
溢れた瞬間の連続GPU画像は取得していない。欠けのframe数は診断、参照先とpaddingは模擬GPUで検証する。

Apple M4 / Metalへ接続する環境はなく、Macの前後測定と40msスパイクのframe単位の相関は未検証。
推測値を記載しない。他のbeatoraja互換スキンやBMZ同梱スキンの実機画像比較、
全OS/backendの表示、実際のscanout間隔、RSSの比較も未実施。

行全体を保護するため、少数の現役グリフが多数の行に散らばると全消去が残る。
全ての単発スパイクが消える変更ではない。起動後のGPUテクスチャ拡張に伴う全転送も残る。

## マージ判断

Windowsでは全消去の頻度、復旧frameの平均、容量不足の未描画要求が減り、通常の文字準備に
大きな悪化は観測しなかった。一方、p99.9・最大値は全条件で改善せず、Macの実測と40msの相関は未確認である。
既存all-targets Clippyも失敗するため、依頼された全環境の確認完了としては扱わず、Draftで提示する。
