# 曲更新がbeatorajaより遅い問題の調査と改善

2026-11-10に、「BMZの曲更新がbeatorajaより遅く、Everything連携をONにしてもあまり改善しない」という
報告を調べ、段階ごとに計測して採用を判断した記録です。現在の仕様は
[曲の取得元とスキャン](../../docs/song-sources.md)、[Everything連携](../../docs/everything.md)、
[設定](../../docs/settings.md#ライブラリ)を参照してください。

## 条件

- Windows 11、曲はNVMe SSD（G:）、論理24コア、release build
- 実ライブラリ10 root、126,557譜面、書庫830個。`library.db`（約830MB）のコピーをscratchpadに置き、
  `BMZ_DATA_DIR`等で本番のDB・configと分けた。計測素材はローカルのscratchpadだけにあり、共有しない。
- `songs load`（差分）と`songs reload <root>`（全件再解析）のCLIで計測し、各系列は初回を捨てた3回。
  初回はmigrationや失敗譜面の記録を含むため比較に使わない。OSのファイルcacheが温まった状態の値で、
  cacheを空にした状態は計測していない。
- Everything 1.5.0.1418b。普段はサービス（`-svc`）だけが動き、本体は起動していなかった。
  Everything経由の計測では本体をトレイ常駐で一時起動し、計測後に終了した。
- beatorajaは実行しておらず、比較は参照ソース（`.local/beatoraja/`）の読み取りによる。

## 見つかった原因

- 画面の更新操作（Select画面のF5 / UPDATE FOLDER、設定のroot再読込、「ライブラリを再スキャン」）が
  すべてforce付きで、変更のない譜面も全件を解析していた。beatorajaのフォルダ更新・楽曲更新は
  更新日時の差分で、全件更新は別の操作。全件の解析は約75譜面/秒で、全root（126,557譜面）では約28分かかる。
- Everythingは使われていなかった。本体が起動しておらずサービスだけでは検索に応答しないため、
  全rootが通常探索へ黙ってフォールバックしていた。
- Everythingを使うと、かえって遅くなった。隠しファイルの除外（既定ON）のため、結果のファイルと
  親フォルダごとに属性を逐次statしており、Everythingの属性索引は既定でOFF（`index_attributes=0`）だった。
- 差分スキャンにも毎回の固定費があった。parseに失敗した譜面102件の再解析、rootごとの`chart_files`全行の
  再読込と文字列正規化、登録済み全譜面の再stat、書庫索引の3回の読み直し（索引cacheは32個まで）、
  変化のない世代・フォルダフラグの書き込みがあった。
- 暗号化などの未対応書庫があるrootは「不完全」として削除判定が止まり、AppleDoubleの`._*.bms`などの
  ゴミ54件が曲として登録されたまま残っていた。

## 判断

- root整理（`reconcile_configured_song_roots`）は0.61秒→0.08秒になった。描画スレッドの外へ移すには
  スキャン中の設定変更と整合させる状態管理が必要で、全体同期の最後の一回分に見合わないため移していない。
- 発見済み登録の再statは、スキャン中の数秒間に消えた譜面を同じスキャンで消すためだけに1.76秒かかっていた。
  beatorajaもこの確認をしないため廃止し、次のスキャンで消す仕様にした。
- 隠し属性の確認は、通常探索（Windows）では差がなかった（1.33秒と1.33秒）が、Everythingでは約11秒かかった。
  並列化しても同規模の並列stat（118k件で1.76秒）からEverything探索（約1.1秒）より遅くなり、
  探索方法で結果が変わるのも避けたいため、属性の確認も削除した。
- 署名を認識できない書庫は破損と区別できないため、未対応扱いにせず従来どおり削除判定を止める。
- Everything 1.5 alphaのインスタンス名付き起動は、everything-ipc 0.1.4（上流のHEADも同じ）が
  ウィンドウクラス名を`_(`なしで組み立てるため接続できない。依存クレートの変更が必要なため対応していない。

## 全件再解析のCPU時間（同日追記）

全件再解析では1譜面あたり約51msのCPU時間がかかっていたが、`bmz-chart`の取り込みを単スレッドで測ると
平均9.3ms/譜面だった。差は解析ではなく、スキャン中のファイルシステムへのアクセスだった。

- 計測には`#[ignore]`のベンチを使った。`import_stage_timing`（取り込みの段階別）、
  `normalize_stage_timing`（normalizeの段階別）、`import_thread_scaling`（スレッド数ごとの経過時間）で、
  `BMZ_IMPORT_BENCH_DIR`に譜面のフォルダを指定して`cargo test -p bmz-chart --release --lib -- --ignored --nocapture <名前>`で実行する。
  管理者権限がなくETWのサンプリングプロファイラを使えないため、段階ごとの経過時間で切り分けた。
- スキャン中のカーネル時間は151秒中81秒（EVENTS）で、1譜面あたり約26msだった。
- プレビュー音声の解決（bmz-playerの`find_preview_prefix_audio_file`）が、`#PREVIEW`のない譜面ごとに
  フォルダ内の全エントリを名前を見る前にstatしていた。キー音が数百〜数千あるフォルダで、譜面ごとに繰り返していた。
  名前で`preview*`の候補を絞ってからstatするように変えた。
- BGAの解決（`resolve_bga_asset_path`）が、資源の存在確認をOFFにしたスキャンでも、`#BMP`の行ごとに
  同名の別拡張子の候補を最大十数回statしていた。`#BMP`が234行ある譜面で約95ms/譜面だった。
  スキャンはBGAの解決結果を保存しないため、`AssetLookup::Declared`で宣言どおりのパスのまま取り込むようにした。
  再生時（`AssetLookup::Resolve`）の動作は変えていない。
- mimallocに差し替えた実験（scratchpadの別プロジェクト、リポジトリには入れていない）では、単スレッドが12.0秒→9.5秒に
  なるだけで、並列時の伸びの悪さは直らなかった。アロケータのロックは主因ではなかった。

| 計測 | 変更前 | 変更後 |
|---|---:|---:|
| EVENTS（3,126譜面）の全件再解析 wall | 10.8〜12.4秒 | 3.7秒 |
| 同 CPU / カーネル | 151〜160秒 / 81秒 | 44秒 / 4.4秒 |
| 全root（126,557譜面）の全件再解析 wall | 約28分（調査開始時の外挿） | 170秒 |
| 取り込み 単スレッド平均（EVENTS 2,807譜面） | 9.3ms | 7.4ms |
| 取り込み 24スレッドでの伸び（1,200譜面） | 4.5倍 | 11.3倍 |

i9-12900K（Pコア8、Eコア8、論理24）のため、24スレッドの伸びの上限はおおむね12〜14倍。
変更前後のEVENTSのDB（`charts`の41列、`chart_analysis`、`chart_import_warnings`）は完全に一致した。

変更後の単スレッドの内訳は、bms-rsの`parse_bms`が3.66ms（49%）、BMZ側のテキスト前処理
（BGA行・`#TEXT`・ヘッダー・空メタデータの抽出など）が合計約2.5ms、normalizeが0.85ms。

## 未確認・残課題

- 取り込みの約半分は外部クレートbms-rsの構文解析で、BMZ側では変えていない。
  BMZ側のテキスト前処理は全文の複製と行走査を繰り返しており、まとめれば数十%の短縮余地がある。
- 書庫索引cacheが32個までのため、アプリ内で繰り返しスキャンすると探索時に830個の索引を毎回読む。
  CLIは毎回新しいプロセスなので、この影響は計測していない。
- OSのファイルcacheを空にした状態、macOS / Linuxの実機、アプリ画面（新しいボタン、トースト）は未確認。
