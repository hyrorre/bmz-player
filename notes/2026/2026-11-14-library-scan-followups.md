# ライブラリの譜面統計・探索の高速化

[11月10日の計測](2026-11-10-song-update-performance.md)の続き。現行のスキャン仕様は
[曲の取得元とスキャン](../../docs/song-sources.md#走査と更新)を参照。

## 条件

- Windows、論理24コア。基準は `9ac37d68`。ASIO SDKを取得できなかったため、すべて
  `cargo build -p bmz-player --release --locked --offline --no-default-features --bin bmz-player`
  で揃えた。
- 通常探索を使い、`BMZ_DATA_DIR`、`BMZ_CACHE_DIR`、`BMZ_LOGS_DIR` を版ごとに分けた。
  EVENTSは初回取り込みの後、変更なしの `songs load` と `songs reload` を各3回実行。
  表はCLIの `Timing` に出る本体時間の中央値。初回を除く。生ログ・計測用素材は
  `.local/scan-perf-20261114/` にあり、共有しない。
- INSANEの差分計測は、本番DBのコピーで取り込みバージョンだけを10に揃え、変更のあった1,300件を
  両版で同じように取り込んだ後に行った。変更なしの測定用のDBであり、実データの更新手順には使わない。

## 段階ごとの結果

| 段階 | EVENTS 全件再解析 | EVENTS 変更なし |
| --- | ---: | ---: |
| 基準 | 3,512 ms | 120 ms |
| 1. 譜面統計の並列化とBPM探索の短縮 | 2,652 ms | 116 ms |
| 2. プレビュー候補の共有 | 3,080 ms | 112 ms |
| 3. BMS・PMS前処理の割り当てを削減 | 2,708 ms | 110 ms |
| 4. 差分照合・削除判定の割り当てを削減 | 2,825 ms | 113 ms |

実行順を反転させながら各4回行った別の測定では、EVENTSの基準は3,830 ms、最終版は4,125 ms。
この系列では同時に別のテストが動き、探索が約0.09〜0.41秒、コミットも大きく変動した。
最終ビルドと基準を交互に各3回再計測すると、書き込み区間は中央値887 → 646 ms、本体は
3,493 → 3,586 msだった。EVENTS全体で再現する短縮は確認できなかった。各案の効果は対象を絞った
以下の計測で確認した。

### 1. 譜面統計

主BPMは譜面内の時刻順BPM変化を二分探索し、同時刻では最後のBPM変化を使う。ノーツの集計順は維持した。
通常ファイルでは、譜面統計の計算と保存用文字列への変換を解析ワーカーで行う。
CLIとアプリのログにワーカーごとの経過時間の合計と通常ファイルのコミット時間を追加した。

BPMが交互に変わる2.4万イベントと1.2万ノーツを持つ自作譜面8件の再解析では
**568 → 56 ms**。書き込み区間は **524 → 10 ms**。DBの譜面統計と全登録結果が一致した。
以前に全ルートで観測した74秒のバッチについては、今回の結果から原因を断定できない。

### 2. プレビュー候補

通常譜面の `#PREVIEW` が解決できないときに行う `preview*` の列挙を、同じフォルダ内で共有する。
候補がない場合もそのスキャン中は共有する。明示パスと別拡張子の解決を優先する。

48フォルダに各24譜面と300素材名を置いた自作データの全件再解析では **138 → 89 ms**。
解析側の時間は **110 → 59 ms**。同じデータに1譜面を追加したときは27 msと30 msで各1件を登録し、
削除後はどちらも1,152件に戻った。最終版でも1件追加・削除を確認した（12 ms、10 ms）。
EVENTSでは前後の範囲が重なった。

### 3. BMS・PMS前処理と bms-rs

UTF-8は元のbytesを借用し、PMSのレイアウト判定と取り込みで同じデコード結果を使う。
既存のPMS診断の件数と順序を保つ。Kaleidの事前判定はASCIIチャネル名をバイトで比較する。

EVENTSのBMS系1,200譜面の段階計測は、トークン処理が **2.98 ms/譜面**、字句解析が
**0.57 ms/譜面**、再生可否の確認が **0.37 ms/譜面**。依存のローカルコピーで字句解析時の一時
`Vec` をなくした試行では、700譜面を前後各2回計測し、字句解析が **0.562〜0.607 →
0.318〜0.335 ms/譜面**、取り込み全体は **7.6〜8.1 → 7.4〜7.7 ms/譜面**。
EVENTSの3,025譜面に4通りの乱数指定を与え、字句解析変更前後のダイジェストが一致した。
取り込み全体の差が小さいため、依存の差し替えは試行のみとした。

### 4. パス照合

発見時の正規化済みパスを差分照合と書庫登録確認でも使う。削除判定ではDBの登録パスを
一度読み、発見済みのパスを除いたものだけ正規化して、ルート範囲とファイルの有無を確認する。

INSANEの69,431譜面を対象にした変更なしの差分更新では、実行順を反転して計測した
後半3回の中央値で、本体 **1,117 → 1,087 ms**、削除判定 **169 → 137 ms**、
差分照合 **32 → 22 ms**。両版の初回の探索時間は3秒を超えたため、この比較から除いた。

## 出力の比較

EVENTSの3,126パス（成功3,123、失敗3）では、パスを基準にしたファイル情報とハッシュ、譜面情報、
譜面統計、警告の順序と内容が全段階で一致した。並列取り込みで変わり得る行IDと実行時刻は比較から除いた。
INSANEの案4前後と、自作の譜面統計・プレビュー素材の比較でも同じ項目が一致した。
実アプリでの操作、Everything、macOS/Linux、全10ルートのバージョン更新を通した再計測は未実施。

## 自動検証

fmt、ワークスペースのcheck、全ターゲットClippyをWindowsで実行した。Rustの検証は
`--locked --offline --no-default-features`。スキャン・ライブラリDB・譜面素材のテストは
116件通過、2件ignore。サンドボックス内でjunctionを作成できなかった重複rootのテストも、
サンドボックス外の実行で通過した。
