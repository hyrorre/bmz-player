# 段位認定・コースの途中終了時のBPとCB

[Issue #158](https://github.com/hyrorre/bmz-player/issues/158) の例は、1,710ノーツ中PGREAT 1・POOR 5で閉店した段位の単曲。残り1,704ノーツを加えた履歴のBP・CBはともに1,709だが、単曲IRには5が送られていた。

## 調査した経路

| 経路 | 結果 |
| --- | --- |
| 段位の単曲IR・更新時のみ送信 | 送信用の複製でランプを先にNoPlayに丸め、FAILED時の未処理分を失っていた。送信値とベスト比較には元のプレイ結果を使い、記録するランプだけを丸める。Bokutachi固有のBP・CB再設定も共通処理にまとめた。 |
| 単曲のゲージ枯渇・手動中断 | ローカル履歴・ベスト、リザルト、リプレイ枠、oraja_helperは元の結果を使う。単曲と段位の両方で、同じスコアを2回出したときの送信件数と空POORの扱いを回帰テストで確認した。 |
| BMZ IRからの履歴復元 | 即時送信の処理済み数が省略され、サーバー側で全ノーツ処理済みになっていた。即時送信は採点済みの実数を渡す。一括送信でも、非消費BADなどで判定数と処理済み数がずれる場合は、ローカル履歴のBP・CBに共通する未処理分から復元する。 |
| BMZ IRの単曲詳細 | 判定数由来のBPを表示していた。スコア詳細のBP欄には、そのプレイの送信値を使う。 |
| コース全体 | BPは途中終了曲の残りと未開始曲をすでに含んでいた。リザルトと保存済みベストのCBは各曲のCBだけを足していたため、未開始曲があると不足した。プレイした全曲の判定内訳が揃う場合は、コースBPから空POORを引けば、ステージ間で中断した場合も同じ規則で計算できる。 |

回帰テストはローカルのSQLiteとIR送信キューを使った。報告されたWindows実機・対象譜面での再プレイと本番IRへの送信は未実施。既存の送信済みスコアを修復する移行処理は含まない。

保存・送信の仕様は[スコア保存](../../docs/score-persistence.md)と[IR](../../docs/ir.md)に記載した。
