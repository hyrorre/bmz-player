# 起動・楽曲決定ロードの追加最適化

先行する[起動と選曲操作の改善](2026-10-26-startup-select-latency.md)後に残った、
Selectスキンの同期準備、Decide準備と譜面先読みの直列実行、キー音の再デコード、
書庫の初回読み込みを対象とする。スキンの演出時間は変更しない。

## 実装

- フォントとsource画像のデコードを同じRayon poolで並行する。
  Luaの文書構築・ロード時乱数の評価は並行化より前に完了する。
- 起動時のSelect skinをworkerでデコードし、window / surface / egui初期化と重ねる。
  最初のフレーム前に適用を待ち、画面サイズに依存するLuaの再要求も既存の世代管理を使う。
- 楽曲決定では、Decide skinの待機とSTAGEFILE / BACKBMPの準備より先に音源先読みを開始する。
  Play skinもDecideの待機前に要求する。Select / Decideの再ロードには既存の
  適用済みフォント確認を使い、CPUキャッシュから退避したフォントも再デコードしない。
  フォント本体・bitmap pageが変わった場合は既存のキー判定で再読み込みする。
- Playの音源ロードは容量制限付きのPCMキャッシュを使う。通常ファイルのサイズ・更新日時・作成日時
  （Unixではinode / ctimeも）、書庫で実際に読み込んだbytesの同一性、出力レート・VOLWAVを確認する。
  失敗を保持せず、デコード中の更新もキャッシュしない。PCMとキャッシュが保持する書庫bytesの
  合計上限は512MiB、エントリ数は4,096。PCMはVecの長さでなく確保容量を計上する。
  再生側のArc所有は退避によって破棄されない。
- キー音の候補確認を同じdecode workerへ移す。最初の既存候補で成功したら、残りの拡張子は
  statしない。デコード失敗時は従来の全候補と順序を使い、別名宣言が同じ実ファイルへ解決された
  場合も1回だけデコードする。region登録順・進捗の単調性は維持する。
- Selectで選択が400ms安定すると、solid書庫を低優先度の単一workerで先読みする。
  対象フォルダの宣言サイズが256MiBを超える場合は行わない。選択変更時のキャンセル、
  同じ書庫を読むPlayとの待ち合わせ、世代の確認、未使用資源の破棄を行う。
  既存の直近3セット・1GiBの資源キャッシュ上限は変更しない。

仕様は[gameplay-runtime](../../docs/gameplay-runtime.md)、[書庫楽曲](../../docs/archive-songs.md)、
再計測手順は[development](../../docs/development.md)を参照。

## 計測条件

- 比較元は`8e99ef7d`をrelease buildしたもの。
- Windows、Core i9-12900K、RTX 5090 / Dx12、4K borderless、ECFN Select、
  ASIO4ALL（実際の出力44,100Hz）、既存の77,408譜面のsnapshot。
  元のconfig / DBは更新せず、`.local/performance/load-opt-20261026/`の隔離データを使う。
- OBSとIR providerを計測用コピーで無効化。起動は120フレームで終了し、
  アプリ内起動タイマーからsuccessful first presentまでを比較する。
- サンドボックス内の実行は音声初期化付近で異常終了したため、成功値は通常環境で揃えた。
  コンパイル・テストを計測と同時に実行しない。

## 起動

両バイナリを慣らした後、交互に4回ずつ測定した。

| | 4回の値 | 中央値 |
|---|---|---:|
| 変更前 | 1,702 / 1,688 / 1,688 / 1,675ms | 1,688ms |
| 追加最適化 | 1,136 / 1,170 / 1,167 / 1,183ms | 1,168.5ms |

約30.8%の短縮。`runs/baseline-30..33`と`runs/final-30..33`で測定した。
初回描画までにSelect skinの適用が完了し、残っていた待機は66〜109ms。
別途1,200フレームで撮影した両バイナリのSelect画像も確認し、レイアウト・文字・選曲位置に
差がないことを目視で確認した。全外部スキンの表示互換を証明するものではない。
`font_decode_us`と`source_decode_us`は並行実行されるため、合算してdecodeの壁時計時間にしない。

## 通常ファイルのPCM再利用

隔離DBの2譜面を44,100Hzでロードした。先に4回の全体ロードでキャッシュを準備し、
同じ8 worker・同じ候補確認の実装を使って、キャッシュを使わないFFmpeg loaderと
本番のキャッシュ付きloaderを各4回、順序を交互にして比較した。
譜面parse・音量解析・skin・描画を含まない音源ロード単独の測定である。

| 譜面ID | 音源数 | キャッシュなし4回 | キャッシュあり4回 | 中央値の短縮 |
|---|---:|---|---|---:|
| 29721 | 967 | 229 / 230 / 226 / 230ms | 121 / 116 / 121 / 116ms | 229.5→118.5ms（48.4%） |
| 36102 | 1,119 | 308 / 312 / 311 / 315ms | 136 / 134 / 140 / 136ms | 311.5→136ms（56.3%） |

全体ロードは29721が351→195 / 195 / 195ms、36102が402→236 / 233 / 231msだった。
最初と反復ではPCM以外のキャッシュ状態も違うため、これだけをPCMの短縮率にはしない。
29721には既存の欠損音源が1件あり、966 source / 1,185 regionがロードされた。
欠損数は変更前後・キャッシュ有無で同じ。36102の失敗は0件。

候補確認をすべて並行化するだけの中間版では、反復ロードに約148〜164ms残った。
不要な拡張子確認も遅延させた最終版では上表まで短縮した。
ログは`native_load_latency_bench-lazy-final.txt`。キャッシュ上限はキャッシュが保持する容量であり、
active sample bankや他の画像・書庫キャッシュを含めたアプリ全体のRSS上限ではない。

## 書庫の初回と先読み

既存の書庫ベンチを完全一致で1件ずつ実行した。各プロセスで書庫をscanした後、
フォルダごとに1譜面を選び、48,000Hzで3回ロードする。OSのファイルキャッシュは消去しない。
「初回」はプロセス内の資源・PCMキャッシュが未準備の意味で、再起動直後のcold I/Oではない。

| 書庫 | 初回全体 | 2 / 3回目 |
|---|---:|---:|
| unmei RAR | 1,327ms | 192 / 236ms |
| unmei solid 7z | 1,859ms | 200 / 198ms |
| unmei ZIP | 710ms | 201 / 199ms |
| WAV solid 7z | 3,635ms | 155 / 154ms |
| WAV ZIP | 726ms | 152 / 151ms |

solid 7zだけを事前に読み込んだ別プロセスでは、次の結果だった。

| 書庫 | 先読み自体 | 先読み完了後の初回全体 | 2 / 3回目 |
|---|---:|---:|---:|
| unmei solid 7z | 1,319ms | 522ms | 202 / 201ms |
| WAV solid 7z | 3,403ms | 261ms | 153 / 152ms |

先読みが完了した場合の楽曲決定後の処理を前倒しできた。展開そのもののCPU処理を
速くした結果ではなく、先読み時間も加算すると初回の仕事量は減らない。
選択後すぐ決定した場合や256MiBを超えるフォルダには、同じ短縮を保証しない。
RAR / ZIPは非solidなので先読みを行わない。全5書庫の音源・画像の失敗は0件。
ログは`archive_bench-lazy-final.txt`と`archive_bench-lazy-prefetch.txt`。

## 実際のDecide / Play経路

ECFNの`loadend=3000`、`playstart=1500`は演出の指定であり、処理時間の短縮値には含めない。
Decideにも3秒の表示・fadeout待ちがある。通常ファイルの29721を、各プロセスの初回Playで
自動プレイし、変更前・最終版を3回ずつ交互に実行した。

| 処理 | 変更前3回 | 最終版3回 | 中央値 |
|---|---|---|---:|
| Decide skin全体 | 114.6 / 104.1 / 111.6ms | 14.8 / 14.3 / 17.1ms | 111.6→14.8ms |
| Play skin全体 | 631.5 / 630.9 / 650.5ms | 475.7 / 477.3 / 490.4ms | 631.5→477.3ms |
| 譜面・音源・音量解析の先読み | 594 / 589 / 584ms | 525 / 547 / 531ms | 589→531ms |

各試行のPCMキャッシュは初回のためmissであり、上の再利用ベンチとは異なる。
最終版では音源先読み開始後16〜19msでDecideへ入り、Decide待ち中にPlay skinも進んだ。
Decideフォント3件のpayload skipも確認した。skin全体の時間は画像・GPUキャッシュ状態と
並行化も含む結果であり、短縮のすべてをフォント再利用だけには帰属させない。

Decide表示は変更前3,008〜3,012ms、最終版3,006〜3,012ms。
Play入場から専用gameplay thread開始までも両者とも約3,000msである。
この曲は処理が演出待ち内に収まるため、処理の高速化が同じ割合の待機画面短縮にはならない。
ログは`runs/baseline-play-29721-30..32`と`runs/final-play-29721-30..32`。

最終確認でDecideのフォント再デコードが見つかったため、既存の`reuse_installed_fonts`を
frontend再要求にも使う修正を追加し、上表はその修正・再検証後に取り直した値である。

## 採用しなかった試行

書庫readerの64KiBバッファリングも比較した。WAVのsolid 7z初回は変更前3,651ms、
追加後3,624msで、反復測定での改善根拠にならないため採用しなかった。
sevenzの並列readerも確認したが、ブロック全体の無制限な作業バッファと既存のキャンセル・
読み込み制限の違いがあるため、そのまま有効にはしなかった。
`archive_bench`という部分一致は同モジュールの別テストにも一致するため、
2件同時に走った初回の計測を除外し、完全一致の1件で取り直した。
