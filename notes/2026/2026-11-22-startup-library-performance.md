# 起動とライブラリ再スキャンの計測

Windows 11（build 26300）、Core i9-12900K、release ビルドで検証した。
ライブラリの SQLite バックアップからビルドごとに専用 DB を作った。
登録ファイルは127,720件、登録済み書庫は834件、文書フラグの未確定行は0件。
DX12、1280×720、ウィンドウ表示、WASAPI共有、起動時の自動再スキャン無効で固定した。
同梱スキンと、mz-select / ECFN Decide / WMII_FHD Result の組み合わせを別々に測った。

計測はビルドの実行順を往復させ、各7回のうち初回を除く6回の中央値を採った。
毎回新しいプロセスを起動し、実ウィンドウで10フレーム描画後に終了した。
初回表示は[起動診断](../../docs/startup-diagnostics.md)の
`startup_to_first_present_ms`。生ログと専用DBは作業環境の `.local/startup-scan-perf/` に置いた。

## 文書フラグの補完

起動時とスキャンワーカーの起動時に、文書の有無が未確定のフォルダーを検索する。
従来は補完済みでも通常のフォルダー索引を走査した。
library schema 40 で未確定行のフォルダーだけを収める部分索引を追加した。
既存の譜面データはそのまま使える。移行時に1回、索引作成のため全行を読む。

| 条件 | 変更前（a75579c5e） | 部分索引あり |
|---|---:|---:|
| 同梱スキン・ライブラリ移行と補完 | 159 ms | 12 ms |
| 同梱スキン・初回表示 | 902 ms | 770 ms |
| カスタムスキン・ライブラリ移行と補完 | 159 ms | 12 ms |
| カスタムスキン・初回表示 | 1,158 ms | 1,025 ms |

この比較は索引作成済みのDBを使う。更新後の初回も別に調べた。127,720件のv39 DBを
毎回新しくコピーし、同梱スキンで3版を各6回交互に起動した。初回を除く5回の中央値で、
元のmainは897 ms、表示前に索引を作る版は1,041 ms、表示後に作る最終版は793 msだった。
通常のSelect起動では必要なスキーマ移行と文書フラグの補完は表示前に終える。
650フレームの別試行で初回表示後に保守workerが開始・終了し、終了後のDBがv40、
索引作成済み、登録127,720件、未確定フラグ0件であることを確認した。

## Windows 8.1 互換対応の前後

PR #137 の直前 `c83f0aa77` と取り込み直後 `3a98b21f2` を release でビルドした。
各 exe の `--version` でコミットを照合した。共用 target の初回ビルドで識別子が以前の
コミットを示した通常ターゲット版は除き、空の専用 target で再ビルドして比較した。
MSVC、FFmpeg DLL、DX12、DBとスキンは共通。同じWindows 11で次の値になった。

| ソースと Rust ターゲット | 同梱・初回表示 | カスタム・初回表示 | プロセス開始から初回表示ログ（同梱 / カスタム） |
|---|---:|---:|---:|
| 対応前・stable pc-msvc | 952 ms | 1,177.5 ms | 970 / 1,193.5 ms |
| 対応後・stable pc-msvc | 926 ms | 1,183.5 ms | 943 / 1,201 ms |
| 対応後・nightly pc-msvc | 924.5 ms | 1,155 ms | 941.5 / 1,171.5 ms |
| 対応後・nightly win7-msvc | 920.5 ms | 1,169.5 ms | 939 / 1,186 ms |

同じstableターゲットで比較した対応前後の差は同梱で −26 ms、カスタムで +6 ms。
同じ対応後ソース・nightlyでターゲットを変えた差も同梱で −4 ms、カスタムで +14.5 ms
と方向が分かれた。各6回の分布は重なり、このPCで一貫した起動の悪化は確認できなかった。
nightly は `nightly-2026-11-19` と `-Z build-std=std,panic_abort`。
Windows 8.1 実機および配布物の SxS DLL 配置での起動時間は未計測。
登録されているWindows 8.1 VMは仮想ディスクが2 MiBで、直近のVirtualBoxログも
`No bootable medium found` だった。
当時のプレイ中の結果は[互換対応の記録](2026-11-19-windows-81-compat.md)にある。

## Select・Decide・Result の順序

カスタム3スキンを使い、通常起動の初回表示と、サンプル譜面を直接起動したときの
Decide入場を調べた。Selectだけを先に投入し、DecideとResultを両方とも初回表示後に回すと、
直接起動の要求からDecide入場までが31 → 504.5 msになった（各4回の中央値）。

採用した順序はSelectを同梱PNGより先に投入し、Decideはウィンドウ初期化と並行、
Resultは初回表示後または直接入場時に開始する。部分索引を入れた同じベースと比較した。
通常起動の初回表示は994.5 → 907 ms、直接起動の要求からDecide入場は34.5 → 22 ms、
アプリ起動からDecide入場は1,052 → 920 msだった（各6回の中央値）。

## スキャン

通常探索を使った。時間はCLIの `Timing` にある処理時間で、DBはすべて計測専用コピー。

| 比較条件 | 変更前 | 変更後 |
|---|---:|---:|
| 親子を交互に更新、BHT（44件）の部分スキャン | 125 ms・44件再解析 | 29 ms・全件スキップ |
| 同じ手順のEVENTS（3,359件）のスキャン | 339.5 ms・44件再解析 | 238 ms・全件スキップ |
| 256譜面の生成ZIP、強制再解析の書庫区間 | 669 ms | 286 ms |
| 同じZIPの探索を含む全体 | 940 ms | 558 ms |
| 起動時自動更新ON・既存3,360件、同梱スキンの初回表示 | 882.5 ms | 685 ms |

親が登録済みの譜面を子ルートでも照合できるようにし、削除候補では無関係なパスを
正規化する前に除外した。子の5回と親の6回の中央値。強制更新は毎回読み直す。
生成ZIPは譜面ごとに120個のキー音名を置いた。音声データは空で、プレビューの
名前解決を測った。明示ファイルの拡張子代替128件とフォールバック128件について、
登録パス・SHA-256・プレビュー・文書フラグを照合した。

起動時の自動更新では初回表示後に既存のスキャンキューで2ルートを探索し、
3,360件スキップ・失敗0件で終了した。空のDB、直接起動、CLIは同期のまま。
移したのは表示前の待ち時間で、バックグラウンドの探索は引き続き実行する。

## 追加の比較

- 単一ドライブの部分スキャンで既存のパス索引を使った。登録の大半がG:にあるDBで、
  C:の同梱サンプルは26 → 2 ms（削除候補の探索24 → 0 ms）。
  G:の子44件は29 → 31 msだった。大小文字、区切り、拡張パス、Unicode表記を
  最終的なルート照合で扱う。
- 全登録範囲を照合する `songs load` で、残すパスの一括コピーを省いた。
  C:・G:の登録を無効ルートで保持し、127,720件の範囲照合だけを比較したとき、
  `scope` は93.5 → 67.5 msだった。
- スキンカタログの列挙で、通常ファイルのうち対象外の素材を実体パス解決の前に除外した。
  カタログ走査は2,375 → 1,207 ms、初回表示は728 → 765.5 msだった。
  続いて探索を初回表示後まで待たせる比較を行うと、初回表示は752.5 → 728 ms、
  走査開始から終了は1,190 → 877.5 msだった。設定やLR2が先に一覧を要求した場合は
  そこで開始する。別系列のため各改善幅は加算しない。
- 自動再スキャンで発見した通常ファイルは、WAV/OGGなら譜面・書庫・文書の拡張子判定を
  省いた。EVENTS（3,359件）の探索は197.5 → 187 ms、INSANE（68,893件）は
  386.5 → 360 msだった。どちらも通常探索で全件スキップした。
- コースの譜面リンク照合も調べた。実際と同じトランザクション内で、3,356組のハッシュと
  コース項目1,657件を照合した条件では、既存の索引照会が2.2〜2.7 ms、JSONで256件ずつ
  まとめる案が3.1〜4.1 msだった。該当するコース項目は0件で、実装は変更しなかった。
- 文書フラグはフォルダー索引順に照合し、読み込みに失敗した書庫があるときだけ
  そのフォルダーを除外する。INSANEのフラグ更新区間は50.5 → 41 ms、
  全体は652 → 637.5 ms。EVENTSではフラグ更新はどちらも2 msだった。
- DX12（GeForce RTX 5090）で画像パイプラインの共通WGSLとlayoutを初期化時に共有した。
  全blend用のパイプラインは起動時に作る。各9回中、初回を除く8回の中央値で、
  surface設定ログからattach完了までは同梱124.5 → 118 ms、カスタム137 → 130.5 ms。
  初回表示は同梱799 → 788 ms、カスタム881 → 865.5 msだった。
- 変更のない通常譜面は、所属ルートで取得した指紋を1回照合すればスキップできる。
  親・子ルート間の追加照会を、そのルートの指紋が取れなかったパスに絞った。
  10ルート127,720件の個別比較では、指紋取得と変更判定の合計が227 → 215 ms、
  スキャン本体は1,348 → 1,327.5 ms。最初の1回を除く6組すべてで照合時間が短く、
  子44件のスキャンは両版31 msだった。
  最終実装と直前版を再比較した6組では、照合時間の中央値は219 → 217 ms、
  スキャン本体は1,334 → 1,314 msだった。照合区間の短縮幅にはばらつきがある。

## 統合版と元のmainの比較

同じWindows 11・DX12環境で `a75579c5e` と `3fd04d0a` 相当のreleaseを交互に実行した。
毎回新しいプロセスで、最初の1回を除いた中央値。通常起動と直接起動は各6回、
カタログ完了は各3回、スキャンは各4回。スキャン本体の `total` と、
設定の読み込み・DB移行・全範囲の照合・終了を含むプロセス時間を個別に測った。

| 条件 | 元のmain | 統合版 |
|---|---:|---:|
| 127,720件、自動更新OFF、同梱スキンの初回表示 | 900.5 ms | 652 ms |
| 同じDB、カスタム3スキンの初回表示 | 1,167.5 ms | 775.5 ms |
| カスタムスキン、起動開始から直接指定したサンプルのDecide入場 | 1,163.5 ms | 791.5 ms |
| 3,360件、自動更新ON、同梱スキンの初回表示 | 845 ms | 619 ms |
| 同じ3,360件、カスタムスキン、起動開始からカタログ探索完了 | 2,552 ms | 1,599 ms |
| 設定済み10ルート、変更なし127,720件、スキャン本体 | 1,397.5 ms | 1,325 ms |
| 同じ10ルートの `songs load` プロセス全体 | 1,746 ms | 1,508.5 ms |
| 空DBにEVENTSの3,359件を新規取り込み、スキャン本体 | 3,916.5 ms | 3,644 ms |
| 生成ZIPを強制再解析、スキャン本体 | 1,027.5 ms | 541 ms |

10ルートはいずれも読み取り可能で、全件スキップ、失敗0件だった。両版のDBを比較し、
パス、ハッシュ、解析状態、サイズ・mtime、譜面とのリンク先ハッシュ、タイトル、
プレビュー、文書フラグ、取り込みバージョンの組が127,720件すべて一致した。
両DBのSQLite quick_checkと外部キー検査も通った。生成ZIPは両版とも256件成功・
警告256件・失敗0件。Result直接起動ではWMII_FHDのNormal用要求とフォントinstall、
Result入場、10フレーム描画後の正常終了を確認した。

EVENTSの新規取り込みは両版とも3,356件成功、同一のBMSON 3件が失敗、警告6,340件。
最終試行のDBを全登録と同じ項目で比較し、3,359件の組が一致した。
10ルートの全件スキップ試行では最終版の探索が916 ms、指紋取得が206 msを占めた。
計測対象はローカルドライブの通常探索で、Everything利用時・ネットワークドライブの性能は未計測。

Windowsで `cargo fmt --check`、workspaceの `check --locked`、
`clippy --workspace --all-targets --locked -- -D warnings`、
`test --workspace --locked --no-fail-fast` が成功した。通常テストは
5,946件成功・144件ignore（子プロセスのテスト出力は二重に数えていない）。
追加でbmz-renderのGPUテスト8件を明示実行し、
RGB反転のalpha、減算、スライス画像、テクスチャ更新、ambient 2件、
Qwilight合成、内部解像度の拡大表示を画素読み戻しで確認した。
同じGPU変更を含むビルドでWindowsのOpenGLとVulkanも個別に起動し、
両方でRTX 5090の指定backendを選択、1280×720のsurfaceを構成しスクリーンショットを保存した。
同梱submodule 3種は固定版、カスタム3スキンは実際のインストール先を使用した。
通常の比較はOSキャッシュを消去していない。手動試奏、macOS/Linuxの実機は未検証。
