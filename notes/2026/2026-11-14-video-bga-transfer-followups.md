# 動画BGAのバッファ再利用・表示領域に応じた縮小・GPU色変換

2026-11-14に実装・計測しました。[キャンバス寸法に応じた縮小](2026-11-14-video-bga-playback-resolution.md)に続く改善です。

## 実装

1. ライブBGAのデコーダごとに使用済み画素バッファを1本まで保持します。描画スレッドはロック待ちせずに返却し、デコーダは後続のフレームへ再利用します。FFmpeg自身の内部バッファは従来どおりです。
2. 評価済みの描画計画からBGAの描画先とUVを読み、転送に必要な寸法をデコーダへ渡します。複数箇所に描画する場合は軸ごとの最大値を使います。クロップによる拡大分も含め、64 px単位で切り上げます。元動画の寸法はスキンの配置に引き続き使います。
3. 縮小不要でRGBA換算8 MiBを超える対応素材は、8 bit YUV420の3面を転送してGPUでBT.601のリミテッドレンジからRGBAへ変換します。縮小が必要な素材、対象外の色空間やレンジ、スキン内動画、書き出しには従来のRGBA変換を使います。

継続仕様は[ゲームプレイ実行系](../../docs/gameplay-runtime.md)を参照してください。

## 計測

Windows、RTX 5090、DX12、Fast Vsyncの実効Mailbox、目標240 FPS、自動演奏で、各案を加えた最適化ビルドを直前の版と比較しました。初期基準の実行ファイルは `267f9816` です。3840×2160・30 fpsのH.264素材を使用し、1枚と2枚の条件では3840×2160のウィンドウを使用しました。2枚の条件では異なるBGAアセットとして同じ映像をBaseとLayerで同時に再生しました。小窓条件は1920×1080のウィンドウで、1280×720のスキンキャンバスに320×180の表示先を設けました。

Playの最初のsnapshotから5〜21秒を集計しました。描画開始間隔はアプリのログ、実表示更新間隔はPresentMon 2.3.1の `MsBetweenDisplayChange` です。計測中の表示経路はComposed Flipです。

| 段階と条件 | 描画開始間隔 p99 | 実表示更新間隔 p99 | 実表示10 ms超 |
|---|---:|---:|---:|
| 1. 画素バッファ再利用・4K 1枚 | 5.30 → 4.81 ms | 8.38 → 8.39 ms | 6 → 6回 |
| 1. 画素バッファ再利用・4K 2枚 | 12.04 → 9.25 ms | 16.63 → 16.66 ms | 391 → 274回 |
| 2. 表示先に合わせた縮小・小窓 | 4.87 → 4.85 ms | 8.36 → 8.37 ms | 0 → 0回 |
| 3. GPUで色変換・4K 1枚（初回） | 4.86 → 4.78 ms | 8.38 → 8.37 ms | 6 → 0回 |
| 3. GPUで色変換・4K 2枚（初回） | 9.29 → 4.87 ms | 12.51 → 8.38 ms | 283 → 5回 |
| 3. GPUで色変換・4K 1枚（最終版） | 4.88 → 4.83 ms | 8.48 → 8.36 ms | 30 → 1回 |
| 3. GPUで色変換・4K 2枚（最終版） | 8.28 → 4.85 ms | 16.66 → 8.42 ms | 480 → 16回 |

案2の転送寸法は、ログで1920×1080から569×320へ変わったことを確認しました。RGBAの画素データは約91%減りました。この条件では前後とも実表示が安定していました。

案3では4Kの画素データが1フレームあたり31.64 MiBから11.87 MiBへ減り、GPUで変換したRGBAとYUVの入力面を保持します。GPU変換はクロマを2×2画素ごとに参照するため、FFmpegのRGBAと画素単位で一致する保証はありません。

最終版はテスト終了後に測りました。4K 2枚の実表示更新間隔p99は、案2の実行ファイルで初回12.51 ms、最終回16.66 msと変動しました。GPU色変換を加えた版ではどちらの回も約8.4 msでした。最終回の比較では10 ms超が480回から16回へ減り、8 ms超は542回から570回に増えました。

測定の生ログ、設定、スクリプト、素材、各段階のバイナリは `.local/bga-followups-20261114/` に保存しています。このディレクトリはGitで共有しません。

- 同じ4K素材の譜面をDX12で480×270・4 fpsに書き出しました。変更前と最終版の両方で126フレームあり、デコードした映像のSHA-256が一致しました。
- Windowsでfmt、workspace check、全ターゲットClippy、workspaceテストが通りました。workspaceテストは5,585件成功、135件はignoreです。実GPUの色変換テストは別途実行しました。

## FFmpegのRGBA変換先を再利用

beatoraja同梱のJavaCV 1.3.3は、CPUで色変換するときに変換先のBGRフレームを再利用します。BMZでもFFmpegのRGBA変換先をデコーダ内に保持し、変換後の寸法が同じ場合は再利用します。出力寸法が変わると変換先を作り直します。表示側に渡す画素は別のバッファへコピーするため、後続フレームのデコードで表示中のフレームが書き換わることはありません。

元動画にアルファがある場合はRGBA変換後も保持します。案3のYUV420にはアルファがなく、GPUでRGBAに変換するときに完全不透明として扱います。描画時のスキンによる透過は別に適用します。

Windowsで同じ4K・30 fpsのH.264素材を `frame_at_blocking` で順にデコードし、RGBAの受け取りまでを計測しました。各試行150フレームのうち先頭15フレームを除き、変更前→変更後→変更後→変更前の順で実行しました。描画や表示待ちは含みません。

| RGBA出力寸法 | 変更前の p99 | 変更後の p99 |
|---|---:|---:|
| 3840×2160 | 13.04〜13.21 ms | 8.83〜9.34 ms |
| 1920×1080 | 10.16〜10.54 ms | 9.04〜9.23 ms |

各寸法で採取した3フレーム分のRGBAは、変更前後のSHA-256が一致しました。バッファの再利用とアルファ保持の回帰テスト、`bmz-video`・`bmz-ffmpeg` のテスト、書庫内動画と動画書き出しの利用側テストが通りました。計測スクリプトと結果は `.local/bga-followups-20261114/bench-rgba-scratch.rs` と同ディレクトリの `scratch-benchmark.log` に保存しています。

## ライブ譜面BGAのRGB24転送

beatorajaはFFmpegで動画をBGR24へ変換しているため、元動画のアルファを使いません。BMZもライブの譜面BGAを不透明な画像として扱います。対応するYUV420は従来どおり3面を転送し、それ以外のライブ譜面BGAはFFmpegでRGB24へ変換します。GPUが3バイトごとにRGBを読み出してAを補い、既存と同じRGBAテクスチャを描画に使います。スキンによるフェードやブレンドは、そのテクスチャを描画する際に適用します。スキン内動画と動画書き出しのデコード形式はRGBAです。

4K原寸では1フレームの転送量が31.64 MiBから23.73 MiBになります。転送先の入力テクスチャの行末は4バイト境界に揃えます。表示用のRGBAに加えてRGB24の入力テクスチャを保持するため、4Kでは展開の処理と約23.73 MiBのGPUメモリを追加で使います。

WindowsのDX12で、同じフレームを従来のRGBA転送とRGB24転送でそれぞれオフスクリーン描画しました。4K原寸のBT.709タグ付き素材と、569×320に縮小した同じテスト素材を12フレームずつ比較し、すべての出力画素が一致しました。幅5のテストでは行末のパディング、テクスチャの更新と切り替え、50%のスキン透過を含む描画差がないことを確認しました。

比較元は `d3489b56` です。RTX 5090・DX12、Fast Vsyncの実効Mailbox、目標240 FPS、Composed Flipで、Play開始後5〜21秒のPresentMonを集計しました。4KのRGBA／RGB24比較では、同じ非再エンコード素材にBT.709タグを付けてYUV420経路の適用外にしました。小窓の最終転送寸法は前後とも569×320です。ワークスペーステスト終了後に計測順を入れ替え、4K動画2枚は前後各2回、小窓とYUV420は前後各1回測りました。

| 条件 | 描画開始間隔 p99 | 実表示更新間隔 p99 | 実表示10 ms超 |
|---|---:|---:|---:|
| 4K 2枚、RGBA → RGB24 | 33.27〜35.94 → 30.44〜30.87 ms | 41.63〜45.91 → 37.46〜37.49 ms | 479〜514 → 499〜511回 |
| 小窓、RGBA → RGB24 | 62.92 → 53.32 ms | 62.55 → 54.10 ms | 223 → 162回 |
| 4K 2枚、YUV420のまま | 24.99 → 50.75 ms | 25.01 → 54.14 ms | 250 → 284回 |

初回の実表示p99は、4KのRGBAが79.09〜129.08 ms、RGB24が66.64〜87.23 ms、小窓が50.01 → 33.36 ms、YUV420が54.14 → 58.31 msでした。初回の4K計測にはテスト負荷が重なりました。テスト終了後も両ビルドで試行間の変動が大きく、既存YUV420の対照条件でも再計測の前後で値が動きました。RGB24の4Kでは再計測でp99が短くなりましたが、10 ms超の回数は同程度でした。この測定から他の環境での改善幅や、対照条件で差が出た原因は判断できません。

fmt、workspace check、全ターゲットClippy、workspaceテストが通りました。workspaceでは5,587件成功、136件はignoreで、RGB24とYUV420のGPUテスト2件は別途実行しました。アプリのログで各試行の転送形式と寸法を確認しました。報告元の譜面、他のGPU、macOS・Linuxは未計測です。計測スクリプトとログは `.local/bga-followups-20261114/` にあります。

### 標準の転送形式を決定

ライブ譜面BGAの標準は `d3489b56` と同じ選択に戻しました。条件を満たす大きな原寸動画はYUV420、縮小した動画や対象外の色空間・形式はRGBAで転送します。表示領域に応じた縮小と、デコード側の画素バッファ・RGBA変換先の再利用を適用します。

RGB24は転送量を25%減らせますが、4K動画2枚で実表示間隔が10 msを超えた回数はRGBAと同程度でした。RGB24の展開と入力テクスチャの追加コストを踏まえ、標準への採用を見送りました。YUV420を前後で交互に各2回測った追加計測では、実表示間隔のp99は変更前8.39〜8.40 ms、変更後8.39〜10.31 msで、前の比較で出た54 ms級の停止は再現しませんでした。

変更後のWindows・DX12の実アプリで、4K原寸の対応動画2枚はYUV420、BT.709の4K動画2枚は原寸RGBA、小窓スキンは569×320のRGBAで転送することをログで確認しました。fmt、workspace check、全ターゲットClippy、workspaceテスト5,586件、実GPUのYUV420変換・RGBA切り替えテストが通りました。
